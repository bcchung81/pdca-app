## 1. 목적과 요구

| 번호 | 요구 |
|---|---|
| R1 완전성 | 과제원장·경평 초안 AI는 그 과제에 해당하는 참고자료를 **빠짐없이, 잘림 없이** context로 봅니다. 한 번에 안 들어가면 조용히 자르지 않고, 자료를 끝까지 읽힌 근거 메모로 넣거나 멈추고 알립니다. |
| R2 적재 통일 | 공통 지식(로컬 파싱 → PGroonga)과 개별 첨부(요청마다 파싱)를 하나의 적재·조립 흐름으로 처리합니다. |

- 월간 점검은 자료 범위를 바꾸지 않습니다. 지침 14와 금기 4에 따라 카드 전용 자료와 검색 결과는 계속 넣지 않고, 모델 분류(§5)만 적용합니다.
- **「context로 제대로 쓴다」의 뜻**: 세 가지가 모두 성립해야 합니다.
  - 들어감: 범위 안 자료가 원문이나 근거 메모로 요청에 모두 들어갑니다.
  - 알아봄: 자료마다 무엇인지, 이 과제와 어떤 관계인지, 숫자 근거로 써도 되는지를 모델이 알 수 있게 표시합니다.
  - 확인됨: 무엇을 넣었고 무엇을 썼는지가 기록되고 화면에 보입니다.

## 3. 원칙

1. **범위는 규칙으로 넓게 정하고, 거르지 않습니다.**
   - 이 사업 + 공통지표(BZ-4) + 사업 미지정 + 기관 공통 자료를 전부 넣습니다.
   - 과제 대응표는 거르는 장치가 아닙니다. 순서·표시와 숫자 근거 범위를 정하는 데만 씁니다. AI 제안이 놓친 조각도 빠지지 않게 하려는 것입니다.
   - 검색(PGroonga)은 화면 검색과 대응표 후보 제안에만 씁니다. 벡터 임베딩(의미 검색)은 쓰지 않습니다(결정 D15). 규칙 범위를 전부 넣으므로 검색에 기대는 곳이 작고, 임베딩에는 별도 업체·기관 자료의 외부 보관·재적재가 따르기 때문입니다.
2. **자르지 않습니다.** 글자 수 자르기를 없앱니다. 토큰 상한을 넘으면 근거 메모 단계로 가고, 그래도 넘치면 멈추고 알립니다.
3. **한 번 읽어 저장합니다.**
   - 모든 자료는 올릴 때 kordoc으로 한 번 읽고 전체 글과 그림 설명을 저장합니다.
   - AI 입력과 숫자·인용 대조는 같은 저장본을 씁니다.
   - **올릴 때 과제 기준으로 미리 준비합니다.** 과제관리카드(운영 59장)는 이미 정해져 있으므로, 자료를 올리면 관련 과제를 매칭하고 과제별 근거 목록표를 만들어 둡니다(§4.2.2·§4.6). 요청 때는 준비물을 읽기만 합니다. **(2026-09-30 재정의로 바뀜 — 공통 지식 매칭은 참고 표시일 뿐 필수가 아니고, 근거 목록표는 저장하지 않고 요청 때 계산하며, 보고서 추가자료는 AI 제안 없이 사람이 과제를 고릅니다. §9 「3-1~3-5 진행」)**
4. **두 기능은 같은 근거 묶음을 씁니다.** 지침이 쓰임을 제한한 자료는 빼지 않고 넣되, 쓰는 법을 프롬프트로 제한합니다. 예를 들어 붙임2는 방법 참고용이고 숫자 근거가 아닙니다.
5. **판단은 AI, 셈·검증·조립은 코드입니다.** 새 프롬프트는 `resources/prompts/<기능>/`에 둡니다.
6. **모델은 기능이 정합니다.** 기능→등급 표 하나로 고정합니다.

## 4. 구조

```
[올리기]  화면 업로드(서버 액션) ─┐        ┌─ 로컬 CLI(큰 문서·일괄)
                                 ▼        ▼
          적재 함수 하나: 원본(저장소) → kordoc 읽기(그림 포함) → 전체 글 저장
                          → 그림 설명(light 모델) 저장 → 조각 나누기 → search_text → PGroonga 색인
                                 ▼  (여기부터 백그라운드 작업 — 올리기는 저장까지만 기다림)
[매칭]    공통 파일      → 규칙 후보 카드 × 조각을 light 모델이 매칭 → 과제 대응표(자동 초안)
          카드 자료      → 그 과제로 확정(매칭 없음)
          보고서 추가자료 → 그 보고서의 과제 중에서 매칭(AI 제안 + 사람이 고름)
                                 ▼
[준비물]  과제별 근거 목록표 = 규칙 범위(기관 공통 + 사업 공통 + 이 사업 지적·실사·전년 절
          + 공통지표·사업 미지정 + 과제 고유) × 매칭 표시(거르지 않음) → 자료·관계·숫자 근거·모델별 토큰
          상한을 넘는 과제는 근거 메모도 미리 / 올리기 결과에 「관련 과제 N개(확정 전)」
                                 ▼
[조립]    요청 때 준비물을 읽어 자료 봉투(같은 형식) + 목록표 (낡았으면 그 자리에서 다시 만듦)
          ├ 상한 안  → 원문 전부(바뀌지 않는 앞부분에 캐시 표지)
          └ 상한 넘음 → 미리 만든 근거 메모(과제와 먼 큰 자료부터, 한 자료가 창보다 크면 구간별)
                                 ▼
[검증]    숫자 대조 = 이 과제 근거의 저장된 전체 글 / 인용 대조 = 넣은 자료 전체
          답의 usedSources 대조 / 결과에 자료별 읽은 방식 기록 / 화면에 넣은 자료·안 쓴 「이 과제 해당」 자료 표시
```

### 4.1 적재 — 함수 하나, 입구 둘

- 입구는 화면 업로드와 로컬 CLI 두 가지입니다. 둘 다 같은 적재 함수(제안 `ingestSource`)를 부르고, CLI는 파일을 넘겨주기만 합니다. 앱이 실행 중에 로컬 경로를 읽지 않으므로 금기 1에 걸리지 않습니다.
- 순서: 원본을 저장소에 둠 → kordoc으로 읽음(그림도 꺼냄) → 전체 글 저장 → 그림 설명 저장(§4.5) → 조각 나누기 → `search_text`(`foldForSearch`) → PGroonga 색인(행을 저장하면 색인이 자동으로 됨) → **과제 매칭(§4.2.2) → 과제별 준비물 갱신(§4.6)**
- 매칭·준비물은 오래 걸릴 수 있어 백그라운드 작업으로 돌립니다. 올리기는 읽기·저장까지만 기다립니다. CLI로 적재한 뒤(`db:seed --knowledge-only`)에도 같은 매칭 작업을 등록합니다.
- **규칙 범위 검산**: 적재 검산(`pnpm knowledge:ingest`, 화면 업로드도 같음)에 「규칙 범위가 기대하는 조각이 있는가」를 더합니다. 검산하지 않으면 새 판이 오면서 키가 바뀌어도 조용히 빠집니다.
  - 확인 대상: 평가 기준 고정 키(`LENS_CRITERIA_KEYS` 6개), 사업별 단위 유형 최소 개수(지적·실사·전년 절·Pool), 과제 목록 행과 `task_map.plan_task_key` 연결
  - 빠지면 종료 코드 1(화면은 적재 실패)로 멈춥니다. 지금은 이 키를 `lib/reports/lens.ts`·`lens-queries.ts`와 테스트만 참조합니다.
- **조각 나누기**는 범용 조각기(제목·쪽 단위, 꼬리표 최소)가 기본입니다. 규칙 범위에 꼬리표가 필요한 핵심 문서만 전용 파서를 유지합니다. 지금 `lib/knowledge/parsers/`에 있는 것은 관리계획(`plan.ts`·`plan-narrative.ts`)·실사·중간보고서·지표 3종·AX·전년 보고서·붙임2입니다.
- **첨부**는 올리는 즉시 읽어 `parse_status`를 `pending → parsed/failed`로 바꿉니다. 요청 때는 저장본만 읽고 다시 파싱하지 않습니다. 읽기에 실패하면 자료 목록에 「AI가 못 읽음」을 표시합니다.
- **판 관리**: 원본 `sha256`과 `parser_version`이 같으면 건너뜁니다. kordoc이나 파서가 바뀌면 다시 읽습니다.
- 큰 PDF(첨부3 476쪽 등)를 서버에서 읽는 데 걸리는 시간은 재지 않았습니다(§11). 오래 걸리면 CLI 입구로 올립니다. 같은 함수라 결과는 같습니다.

### 4.2 범위 — 규칙으로 넓게, 거르지 않음

| 층 | 자료 | 정하는 법 |
|---|---|---|
| 기관 공통 | 평가 기준 6조각 포함 관리계획 서술(`plan_section` 주요사업 트랙 전부 — 평가 결과·시사점·'26 지표 변화·대응방향·작성 착안사항), 자가진단 점검표, 편람 공통 기준, 중장기·기관장 지표, AX 검토 과제, 붙임2 B+·B0(KCA 제외, 운영 11건·약 0.7만 자) | 트랙·단위 유형·등급 규칙 |
| 사업 공통 | 이 사업 편람 지표·Pool, 이 사업 '25 평가위원 의견·중간보고서 지적 전부, 이 사업 실사 질의응답·요청 자료 전부, 이 사업 전년 보고서 절 전부 | 사업 id 규칙 |

- **크기(실측, 로컬 조각 기준)**: 공통 지식만 사업별 25만~29만 자입니다(311~357조각). 여기에 붙임2 B+·B0 약 0.7만 자와 첨부가 더해집니다. 글자→토큰 비율은 아직 재지 않았습니다(§11).

#### 4.2.2 올릴 때 과제 매칭

> **(2026-09-30 재정의로 바뀜)** 아래 표·계기 중 「보고서 추가자료의 AI 제안」과 「과제별 준비물 갱신」은 구현하지 않고 걷어냈습니다. 공통 파일 매칭(`match_knowledge`)은 남아 있으나 참고 표시이고 확정하지 않아도 됩니다. 보고서 추가자료는 올린 뒤 사람이 과제를 고르고(파일 이름에 과제번호가 있으면 미리 체크, 저장해야 확정), 숫자 근거는 확정한 연결만 인정합니다. 구현은 `docs/design/knowledge.md`·`docs/design/report-draft.md`.

과제관리카드는 이미 정해져 있으므로(운영 59장), 자료를 올릴 때 카드 기준으로 미리 매칭해 둡니다.

| 올리는 자료 | 매칭 | 결과 |
|---|---|---|
| 공통 파일(관리 화면 업로드 또는 CLI 적재) | 먼저 규칙으로 후보 카드를 정합니다(사업이 정해진 조각은 그 사업 카드, 사업 미지정·기관 공통 조각은 전체 카드). 그다음 light 모델이 카드 요약(과제명·실행과제·계량지표·Act 지적·AI 활용 칸)과 조각을 보고 「해당 여부·근거 한 줄」을 냅니다 | 과제 대응표 자동 초안(§4.2.1) |
| 카드 전용 자료(카드 화면·경평 과제별 초안 화면) | 없음 — 올린 곳이 그 과제 | 그 과제의 과제 고유 자료(확정) |
| 보고서 추가자료(부서 경평 초안 허브) | 올릴 때 그 보고서의 과제 목록에서 해당 과제를 고릅니다. AI(light)가 먼저 제안하고 사람이 고칩니다. 하나도 안 고르면 「같은 보고서 자료」 | 매칭된 과제: 과제 고유(숫자 근거 인정) / 나머지 과제: 같은 보고서 자료(넣되 숫자 근거 아님) |

- **묻는 방식**
  - 공통 파일은 사업별 조각 묶음을 캐시 앞부분에 두고 카드마다 묻습니다. 묶음은 자르지 않습니다. 묶음이 입력 한도를 넘으면 조각 구간으로 나눠 묻습니다.
  - 59장 일괄이므로 Message Batches(50% 할인, 비동기)를 기본으로 하고, 바로 필요할 때만 차례로 부릅니다.
- **다시 매칭하는 계기**

  | 계기 | 다시 하는 범위 |
  |---|---|
  | 공통 파일 새로 올림·새 판 | 그 문서 × 후보 카드 전체 |
  | 카드 추가, 현행화 반영으로 과제명·실행과제·계량지표 변경 | 그 카드 × 공통 조각 전체 |
  | 카드 보관 | 그 카드의 대응을 보관(되살리면 다시 매칭) |
  | 카드·보고서 자료 올림·지움 | 그 카드(보고서 추가자료는 매칭된 과제들)의 준비물만(§4.6) |
  | 성과관리팀이 대응표를 확정·뺌 | 매칭은 그대로, 그 카드의 준비물(표시)만 |

- **실행**
  - 올리기는 읽기·저장까지만 기다리고, 매칭·준비물은 백그라운드 작업으로 돌립니다(제안 `prep_jobs` 표 + 처리기). 화면 서버 액션의 800초 한도에 묶이지 않게 하려는 것입니다.
  - 자료 목록에 「매칭 중 / 매칭 완료(관련 과제 N개) / 실패」를 보입니다.
  - 처리기 형태(대기열을 비우는 주기 작업, Batches 결과 거두기 등)는 결정 D13입니다.
- **올리기 결과 화면**: 공통 파일은 「관련 과제 N개(확정 전)」를 보이고, 누르면 `/links`의 그 문서 탭으로 가서 확정합니다. 보고서 추가자료는 올리는 칸에서 바로 과제를 고릅니다.
- **매칭 전·실패에도 요청은 됩니다.** 규칙 범위로 모든 자료를 넣고 「이 과제 해당」 표시만 빠집니다. 매칭은 거르는 장치가 아니기 때문입니다(원칙 1, 검증 V1).

### 4.3 조립 — 모두 넣고, 알아보게

**준비물 읽기**
- 요청 때는 과제별 근거 목록표(§4.6)를 읽어 조립합니다. 고르기·토큰 셈·메모는 준비물 단계에서 이미 끝나 있습니다.
- 목록표가 낡았으면(만든 뒤 자료·카드·대응표의 판이 바뀜) 그 자리에서 규칙 범위로 다시 만들어 쓰고, 백그라운드 갱신을 걸어 둡니다. 낡은 목록표를 그대로 쓰지 않습니다(결정 D14).

**자료 봉투**: 공통 지식·첨부·점검표·계량 실적을 모두 같은 형식으로 감쌉니다. 모델이 자료 종류와 관계를 알아보게 하고, R2(통일)를 context 단계에서도 지키려는 것입니다.

```
<자료 id="K-att3-2604/qa/BZ-2/17" 종류="'25 실사 질의응답" 출처="첨부3 실사 답변자료 212~213쪽"
      관계="이 과제 해당(확정)" 숫자근거="인정" 읽은방식="원문">
…전체 글…
</자료>
```

- `관계`: 이 과제 해당(확정·초안) / 같은 사업 / 공통지표 / 기관 공통 / 같은 보고서 자료
- `숫자근거`: 인정 / 인용 대조만 / 참고만 — 코드가 §4.4 규칙으로 붙입니다.
- `읽은방식`: 원문 / 메모
- **공유 층의 봉투에는 카드별 속성을 적지 않습니다**(결정 D17, 2026-09-29). 기관 공통·사업 공통 층의 봉투는 `id`·`종류`·`출처`·`읽은방식`만 적고, `관계`·`숫자근거`와 「이 과제 해당」 표시는 목록표에 둡니다. 과제 고유 층의 봉투는 어차피 카드별이라 모든 속성을 봉투에 적습니다.
- **목록표**: 공유 층 **뒤**, 과제 고유 층 앞에 한 번 둡니다. 자료마다 id·종류·관계·이 과제 해당 여부·숫자 근거·크기를 적고, 「이 과제와 닮은 순서」(id 목록)를 함께 적습니다.
- **순서**: 시스템(지침·문체) → ① 기관 공통 → ② 공통지표·사업 미지정 → ③ 이 사업 공통 → 목록표 → 과제 고유(첨부·점검표·계량 실적) → 카드 → 요청.
  - 구현(2단계)에서는 모든 과제가 같은 ①②를 앞에, 같은 사업만 같은 ③을 그 뒤에 둬 캐시 표지를 ①②와 ③ 두 덩이에 겁니다(시스템 표지까지 3개). 과제원장은 5분, 경평은 1시간(시스템 표지도 같은 수명 — 긴 수명이 앞에 와야 함).
  - 기관 공통·사업 공통 층은 **카드와 상관없는 고정 순서**(문서 → 단위 유형 → 적재 순서)로 둡니다. 그래서 같은 사업의 카드는 이 앞부분이 바이트까지 같아 캐시를 나눠 씁니다(사업 3개 × 공유 앞부분 하나).
  - 「이 과제 해당」 조각도 공유 층의 제자리에 그대로 두고, 목록표에서 표시만 합니다(뒤 층으로 옮기지 않음).
  - 닮은 정도(전년 절 고르기의 글자 두 개 묶음 점수, `lib/reports/prior.ts` 재사용)는 목록표의 「닮은 순서」로만 알립니다. 붙임2 B+·B0 사례도 적재 순서가 아니라 이 목록으로 닮은 사업을 알려 줍니다(지침 09 「과제 유형이 닮은 사업」). 닮은 순서도 준비물 단계에서 미리 정합니다.
  - 첫 초안은 층 안에서도 해당 조각 먼저·닮은 순으로 정렬하고 봉투마다 관계를 적었으나, 그러면 공유 층이 카드마다 달라져 캐시를 같은 카드 안에서만 쓰게 되어 바꿨습니다(§13 V13).
- **캐시**
  - 명시 표지는 시스템 끝과 공유 층 끝(사업별 공유 앞부분)에 둡니다. 여유가 있으면 과제 고유 끝에도 둡니다(요청당 최대 4개).
  - 근거 메모(§4.3 상한 넘음)로 바꾸는 자료가 공유 층에 있으면 그 카드의 공유 층은 카드별이 되어 공유 캐시를 잃습니다. 공유 층 자료의 메모를 카드와 무관한 사업 단위로 만들지는 6단계에서 정합니다(결정 D19).
  - 경평 흐름(구성안 → 집필 → 자동 고치기 → 블록 고치기)은 한 번의 생성이 5분을 넘을 수 있습니다. 캐시 수명은 요청 **시작** 시점부터 세므로, 근거 묶음 표지는 1시간 캐시로 둡니다. 1시간 캐시는 쓰기가 기본 입력 단가의 2배(5분 캐시는 1.25배)이고, 읽기는 Opus 5.5 기준 0.05배입니다.
  - 짧은 호출이 이어지는 작성지원·코멘트는 5분 캐시로 둡니다.
- **토큰 셈과 상한**
  - 부를 모델로 셉니다. 모델마다 토크나이저가 다를 수 있습니다.
  - `count_tokens`로 셀지, 한 번 잰 비율로 어림할지는 0단계 실측 뒤에 정합니다. 상한 근처에서만 정확히 세는 방안도 있습니다.
  - 상한(제안 `INPUT_BUDGET` = 40만 토큰, 입력 한도 100만의 40%)은 실측 뒤 조정합니다(결정 D7).
- **상한 안**이면 원문을 전부 넣습니다.
- **상한을 넘으면** 메모로 바꿀 자료를 이 순서로 고릅니다: 관계가 먼 것부터(기관 공통·같은 사업 중 대응 안 된 것 → 공통지표·미지정 → 이 과제 해당), 같은 관계 안에서는 큰 것부터. 이 과제 해당 자료와 과제 고유 자료는 마지막까지 원문을 유지합니다.
  - 근거 메모: light 모델이 자료 하나 전체와 과제 요약(과제명·실행과제·계량지표)을 읽고 `{사실, 수치, 원문 인용, 위치(쪽·조각·줄), 확신도(높음·보통·낮음)}` 목록을 냅니다. **원문 위치와 확신도는 빠질 수 없는 칸**입니다.
  - 코드가 인용을 원문과 대조해 없는 인용은 버립니다. 위치가 없는 항목도 버립니다.
  - **확신도가 낮은 항목**은 집필 때 그 위치의 원문 구간을 봉투에 함께 넣습니다(상한 안에서). 넣을 자리가 없으면 봉투에 「확인 필요」로 표시합니다. 이 방식은 LLMxMapReduce의 구조화 정보 규약·확신도 보정에서 따왔습니다(§14).
  - 캐시 키는 (자료 sha256, 카드 uid, 프롬프트 판)입니다.
  - 메모는 준비물 단계(§4.6)에서 미리 만들어 둔 것을 씁니다. 없을 때만 그 자리에서 만듭니다.
  - **한 자료가 모델 입력보다 크면** 쪽·조각 구간으로 나눠 구간마다 메모를 만들고 합칩니다. 자료 하나가 커서 멈추는 일은 없습니다.
- 메모로 바꿔도 넘치면 **멈추고 알립니다**(「자료가 너무 많습니다 — N건을 빼 주세요」). 조용히 자르지 않습니다.
- **PDF**: 두 경로 모두 kordoc 글만 넣습니다(결정 D2, 2026-09-29). 지금 API 경로가 PDF를 원본 문서 블록으로 보내는 것(`lib/ai/run.ts` `attachFiles`·`reportStructured`)은 1단계에서 없앱니다.
  - 이유: PDF 원본은 쪽마다 글과 쪽 그림이 함께 토큰으로 잡혀, 카드 자료를 전부 넣으면 큰 PDF 하나로 상한을 넘기 쉽습니다. 또 AI가 보는 글과 앱이 대조하는 글이 같아집니다(P5).
  - 원본을 함께 보내는 것(표·도식 모양을 모델이 직접 봄)은 API 경로를 연 뒤 표본 비교로 다시 검토합니다. 그때도 요청 크기(32MB)·쪽수(600쪽) 한도 안에서만 보냅니다.
  - 글이 없는 스캔 PDF는 그림 설명(§4.5)으로 글을 만들어 둡니다.

### 4.4 검증

- **숫자 대조(없는 숫자 판정)의 근거 = 이 과제 근거의 저장된 전체 글**
  - 범위: 카드, 과제 고유 자료(카드 전용 자료, 이 과제에 매칭된 보고서 추가자료, 계량 실적 입력), 「이 과제 해당」인 실사 답변·전년 절, 과제 고유 자료의 그림 설명
  - 같은 사업의 다른 과제 전년 절·실사는 KCA 사실이긴 하지만, 이 과제 수치로 섞어 쓰는 것을 잡으려고 숫자 근거에서 뺍니다. 인용 대조에는 넣습니다.
  - 같은 보고서 자료(이 과제에 매칭 안 된 보고서 추가자료)도 같은 이유로 숫자 근거에서 뺍니다. 다른 과제의 사진·수치가 이 과제 초안에 섞이는 것을 막기 위해서입니다.
  - context는 넓게, 숫자 근거는 좁게 두는 것입니다.
- **목표치·전년 값은 올해 실적이 아닙니다.** 카드의 목표 칸('26 목표)·전년 실적 칸('25 실적) 값이 올해 실적 자리(추진성과·결과 카드·계량 실적 문장)에 쓰이면 경고하고 자동 고치기를 요청합니다.
  - 지금 경평 초안의 「올해 값이 근거에 없으면 전년·목표로 채우지 않고 `【확인: …】`로 남긴다」 규칙을 코드 검사로 굳히는 것입니다.
  - 실적·목표·벤치마크를 가르는 원칙은 kpi-eval-match의 「목표치와 벤치마크는 실적이 아니다」와 같습니다(§14).
  - 타기관 수치(붙임2)는 이미 인용 대조만 합니다.
- **인용 대조**의 근거는 넣은 자료 전체의 저장된 글입니다. 메모로 넣은 자료도 원문 전체로 대조합니다.
  - 지금 작성지원의 인용 대조(`lib/ai/writer.ts` `verifyResult`)는 공통 지식 조각만 보고 첨부 글은 보지 않습니다. 1단계에서 첨부도 봉투 id로 인용할 수 있게 하고 대조에 넣습니다.
  - 작성지원에는 숫자 대조(`known`)가 없습니다. 둘지는 결정 D18입니다.
- 평가 기준·지적·유관기관 사례는 지금처럼 인용 대조에만 씁니다.
- **usedSources**: 답 스키마에 「근거로 쓴 자료 id」 목록을 더합니다.
  - 코드가 목록표의 id와 대조합니다. 없는 id는 버리고 경고합니다.
  - 「이 과제 해당」인데 쓰지 않은 자료를 화면에 보입니다. 실패로 막지 않고 사람이 판단합니다.
  - 이 목록은 모델이 스스로 적은 것이라 보조 신호입니다. 숫자·인용 대조가 주 검증입니다.
- 결과(초안 `spec.sources`, 작성지원 답)에 자료별 `{id, sha256, 관계, 읽은방식: 원문|메모, 토큰, 뺌 여부}`를 남깁니다.

### 4.5 그림

- **적재 때 한 번** light 모델로 그림 설명을 만들어 글로 저장합니다. 대상은 공통 지식 조각의 그림, 첨부 속 그림(kordoc으로 꺼냄), 사진·이미지 첨부, 글이 없는 스캔 PDF 쪽입니다.
  - 설명에는 보이는 글자·수치·표·장면을 적고 지어내지 않습니다.
  - 봉투에 `종류="그림 설명"`으로 들어갑니다. 설명 속 수치는 그 그림이 과제 고유 자료일 때만 숫자 근거로 인정합니다.
- 이렇게 하면 API·CLI 두 경로가 같은 글을 봅니다. CLI(`--tools ""`)는 그림을 직접 받을 수 없습니다.
- API 경로에서 그림 원본을 함께 보낼지는 결정 D9입니다. 경평 「그림 자리」와 사진 첨부가 이어지는 문제이기도 합니다.
- **첨부 허용 형식**에 이미지(JPG·PNG 등)를 더합니다. 지금 보고서 추가자료 안내와 AI 허용 형식의 불일치를 없앱니다. *(2026-09-30 이번 4단계에서 반영 — `ATTACH_EXTS`에 jpg·jpeg·png·webp·gif)*
- *(2026-09-30 구현: 범위는 첨부 이미지·글 없는 스캔 PDF까지이고 공통 지식 조각 그림·문서 속 그림은 안 함 — 아래 「4단계 진행」)*

### 4.6 과제별 준비물 — 미리 만들어 두기

> **(2026-09-30 재정의로 바뀜)** 저장형 근거 목록표(`card_context_manifest`)·낡음 판정·`build_manifest`는 만들지 않았습니다. 목록표는 요청 때 계산합니다(`buildBundle`의 「이 과제 해당」·닮은 순 앞 30건). `card_context_manifest` 표는 정리 마이그레이션(`20260930110000_prep_cleanup.sql`, 2026-09-30 운영 적용)으로 삭제했습니다.

- **무엇**: 과제마다 「근거 목록표」를 저장합니다.
  - 규칙 범위(§4.2)의 모든 자료와 매칭 결과(§4.2.2)로 만듭니다.
  - 자료마다 id·종류·출처·관계·숫자 근거 인정 여부·판(sha256·parser_version·대응표 갱신 시각)·모델별 토큰 수를 적습니다.
- **상한을 넘는 과제**는 관계가 먼 큰 자료부터 근거 메모를 미리 만들어 목록표에 잇습니다(§4.3 순서와 같음).
- **토큰 셈도 여기서** 모델별로 합니다(`count_tokens` 또는 실측 비율). 요청 때는 세지 않습니다.
- **언제 만드나**: 매칭 작업이 끝날 때, 그리고 §4.2.2의 「다시 매칭하는 계기」마다 해당 과제만 다시 만듭니다.
- **낡음 판정**: 목록표에 적은 판과 지금 판이 다르면 낡은 것입니다. 요청 때 그 자리에서 다시 만들어 쓰고 갱신을 걸어 둡니다(§4.3).
- **두 기능이 같은 목록표를 씁니다**(원칙 4). 기능별 쓰임 제한은 프롬프트에서 합니다.
- **효과**
  - 요청 때 고르기·세기·메모가 없어 빨라지고, 같은 입력이면 같은 목록이 나옵니다(결정론).
  - 화면(작성지원 옆 창·경평 근거 창)에 「준비된 근거 N건 · 토큰 · 메모 N건 · 확정 전 매칭 N건」을 요청 전에 보여 줄 수 있습니다.

## 5. 모델 분류

### 5.1 원칙

- **등급 둘**: heavy = Opus 5.5(`claude-opus-5-5`, 입력 $4·출력 $20 /100만 토큰, 캐시 읽기 $0.20), light = Sonnet 5(`claude-sonnet-5`, $2·$10). 두 모델 모두 입력 한도는 100만 토큰입니다.
- **기능으로 나눕니다**
  - heavy: 판단·창작 — 결과가 곧 평가 논리·짜임·문장 품질이거나 판정인 일
  - light: 정답이 원문에 있고 코드가 검증할 수 있는 일 — 분류·추출·옮기기·국소 수정·그림 설명
- **승격**: light 결과가 결정론 검증(스키마·숫자 대조·원문 인용·칸 경로·판면)에 떨어지면 heavy로 한 번 다시 부릅니다. 승격도 기록합니다.
- **한 작업에는 한 모델**: 초안 한 벌(구성안 → 집필 → 판면 자동 고치기)과 대화 한 줄기 안에서는 모델을 바꾸지 않습니다. 캐시는 모델별이라 바꾸면 캐시를 잃고, 문체도 흔들립니다. 승격 호출만 예외로 캐시를 잃습니다.
- **모델 id는 환경변수로만** 정합니다. 코드에 흩지 않습니다.
- **관찰 모드로 비교합니다** (cascadeflow에서 착안, §14)
  - light로 옮길 후보 기능은 먼저 관찰 모드로 돌립니다. 사용자에게는 heavy 답을 보이고, 같은 입력으로 light를 그림자로 불러 결정론 검증 결과·비용·시간만 기록합니다.
  - 기간과 표본 수를 정해 두고 돌립니다. 그동안 그 기능의 호출 비용이 약 1.5배(light 단가가 heavy의 절반)가 됩니다.
  - 기록을 보고 기능별로 전환합니다(결정 D6).
  - 그림자 답은 화면에 보이지 않고, 기본으로는 저장하지 않습니다. 검증 결과와 토큰만 `ai_requests`에 남깁니다(본문을 저장하지 않는다는 지금 원칙과 같음).
  - 예외: 사람 평가용 표본(§11)만 성과관리팀이 켠 기간에 두 답을 잠시 보관하고, 평가가 끝나면 지웁니다. 본문 저장 원칙의 예외이므로 D6에서 함께 정합니다.
- **외부 라우팅 라이브러리는 쓰지 않습니다**(결정 D16). 승격 규칙이 「검증 실패 시 한 번 재호출」로 단순해 앱 코드 몇 줄이면 됩니다. 의존성을 더해 얻는 것이 적습니다.

### 5.3 설정·기록

- **환경변수**: `CLAUDE_MODEL_HEAVY`(기본 `claude-opus-5-5`), `CLAUDE_MODEL_LIGHT`(기본 `claude-sonnet-5`). 기존 `CLAUDE_MODEL_WRITER`는 heavy의 옛 이름으로 읽어 호환합니다.
- **표 한 곳**(제안 `lib/ai/models.ts`): 기능 → {등급, effort, 캐시 TTL}. 지금 흩어진 effort(API 기본 `medium`, 점검 `CLAUDE_INSPECT_EFFORT`)를 이 표로 모읍니다.
- **CLI 경로**(로컬 개발)
  - 등급별 CLI 별칭 `CLAUDE_CLI_MODEL_HEAVY`(기본 `opus`)·`CLAUDE_CLI_MODEL_LIGHT`(기본 `sonnet`). 지금의 `CLAUDE_CLI_MODEL`은 heavy의 옛 이름으로 읽습니다.
  - 프롬프트는 표준 입력, 시스템 프롬프트는 파일로 넘기므로(`lib/ai/cli.ts`) 입력이 커도 명령줄 길이 한도에 걸리지 않습니다(확인함).
  - CLI 별칭 모델의 입력 한도가 100만인지는 확인하지 못했습니다(§11).
- **기록**
  - `ai_requests.model`에는 이미 실제 모델이 남고, 사용량 화면 단가표(`lib/ai/pricing.ts`)에도 `claude-sonnet-5`가 이미 있습니다.
  - 등급·승격 여부는 새 칸(제안 `tier`·`escalated`)에 남겨 기능별 비용·승격률을 봅니다.
  - 캐시 쓰기는 TTL별로 나눠 남깁니다. 지금은 `cache_write_tokens` 한 칸과 5분 단가(입력의 1.25배) 하나뿐이라, 1시간 캐시(2배)를 쓰면 사용량 화면이 비용을 적게 셉니다. 응답의 `usage.cache_creation.ephemeral_1h_input_tokens`를 새 칸(제안 `cache_write_1h_tokens`)에 남기고 단가표에 1시간 쓰기 단가를 더합니다(1단계).
- **API 차이**(claude-api 참조 기준)
  - Opus 5.5는 thinking을 끌 수 없고 effort 기본이 `medium`입니다. 강제 `tool_choice`를 쓸 수 없습니다.
  - 앱은 구조화 출력(`output_config.format`)을 쓰므로 영향이 없고, effort는 기능별로 명시합니다.
  - 구조화 출력은 citations와 함께 쓸 수 없어서 인용 대조는 지금처럼 코드가 합니다.
  - 캐시 읽기는 대부분 모델에서 입력 토큰 속도 제한에 잡히지 않습니다.
- Claude Code 하위 에이전트의 모델 규칙(haiku 금지, `CLAUDE.md` 작업 방식)과는 별개입니다. 이 절은 앱이 부르는 모델입니다.

## 8. 금기·권한·실행 점검

- 금기 1: 앱은 저장소·DB만 읽습니다. 로컬 CLI는 적재 입구일 뿐 실행 경로가 아닙니다.
- 금기 2: 새 표는 모두 RLS를 켭니다.
- 금기 4
  - 첨부의 글·그림 설명·메모는 그 카드·보고서 범위 칸과 RLS로 묶습니다.
  - 과제 대응표와 공통 검색은 공통 지식 조각만 대상으로 합니다.
  - 그래서 첨부가 다른 카드나 월간 점검으로 새지 않습니다. 보고서 추가자료는 그 보고서에 속한 과제별 초안에만 들어갑니다(지금과 같음).
- 운영 DB 보호: 옮기기·다시 읽기 스크립트는 `guardProduction` 대상인지 정해 두고, 운영에서 돌릴 때 확인을 받습니다.
- 대응표 확정·빼기는 성과관리팀 권한입니다. AI 제안은 자동 초안으로만 들어갑니다.
- **백그라운드 처리기의 권한**
  - 처리기는 로그인 사용자 없이 돌기 때문에 서버에서 비밀 키로 씁니다. 지금은 「데이터 수정은 로그인 사용자 권한으로」가 원칙이므로 새 예외입니다(결정 D13).
  - 쓸 수 있는 표를 매칭·준비물 표(`card_knowledge_scope` 자동 초안·`report_material_cards` 자동 제안·`card_context_manifest`·`source_notes`·`prep_jobs`)로 한정합니다.
  - 작업을 등록할 때는 로그인 사용자 권한으로 확인하고(그 자료를 올릴 수 있는 사람만), 누가 걸었는지 `requested_by`에 남깁니다.
- **실행 시간**
  - 화면의 `maxDuration`은 800초입니다(카드·내 과제·경평 과제별 초안 페이지 등).
  - 입력이 커지면 생각 시간과 첫 응답이 늘어, 집필 + 자동 고치기를 한 서버 액션에서 이어 부르면 800초를 넘을 수 있습니다.
  - 호출은 스트리밍으로 두고, 단계마다 따로 부르게 나눕니다(구성안·집필은 이미 나뉨). 측정에서 넘치면 백그라운드 작업(작업 대기열)으로 옮깁니다(§11).
  - 지금 API 호출은 월간 점검만 스트리밍이고 나머지는 `messages.parse`(비스트리밍)입니다(`lib/ai/run.ts` `structuredApi`). 1단계에서 모두 스트리밍으로 바꿉니다.
  - 경평 두 번째 자동 고치기 기준 `AGAIN_BEFORE_MS`(170초)의 주석은 「함수 제한 300초」이지만 페이지 `maxDuration`은 800초입니다. 실행 시간을 다시 잴 때 맞춥니다.
  - 매칭·준비물·근거 메모는 처음부터 백그라운드 작업이라 이 한도에 묶이지 않습니다. 요청 때 무거운 일이 줄어 집필 호출의 시간 여유도 늘어납니다.
- **속도 제한**: 큰 입력이 분당 입력 토큰 한도에 걸릴 수 있습니다. 캐시 읽기는 대부분 모델에서 한도에 잡히지 않으므로 캐시를 지키는 것이 처리량에도 중요합니다. 일괄 작업(대응표 제안·일괄 점검)은 차례로 부르거나 Batches를 씁니다.

## 0. 요금제

- **Vercel Pro**($20/월): Hobby는 비상업 전용이고 함수 실행 시간이 최대 300초라 이 앱은 배포가 거절됩니다(AI를 부르는 라우트의 `maxDuration = 800`, `app/(app)/**/page.tsx` 여러 곳). 운영은 반드시 Pro.
- **Supabase Pro**($25/월): Free 플랜은 1주 비활성 시 프로젝트가 정지되고, DB 용량 500MB 한도, 백업이 없습니다. 운영은 반드시 Pro.
- **Claude API**: 종량제. 평월 약 $100~200, 보고서 작성이 몰리는 12월은 약 $250~400로 어림합니다(관리자 「AI 사용량」 화면의 실측 토큰 단가 기준).
- **합계 어림**(2026-09-28 요금표 기준): 평월 약 $215(약 30만 원) · 12월 약 $345(약 48만 원). 환율 1,400원 가정, 부가세 별도. 단가 출처: vercel.com/pricing, supabase.com/pricing, docs.claude.com의 요금 문서. 실제 청구는 사용량에 따라 달라지므로 첫 1~2개월은 콘솔 지출 한도·알림으로 확인합니다.

## 1. Vercel

**누가**: 관리자(배포 권한자).

1. 코드는 공개 저장소 `bcchung81/pdca-app`(`main`, 2026-10-26 새 이력 — 옛 비공개 `bcchung81/pdca`는 보관)에 있습니다. Vercel은 Git에 연결하지 않고 이 컴퓨터에서 CLI로 배포합니다(`vercel deploy --prod`) — 공개 저장소에 없는 지침 사본(`resources/harness/pdca/`)도 이 컴퓨터의 파일로 함께 올라가므로, **새로 받은 사본에서 배포하면 AI 작성지원·월간 점검이 지침 없이 실패**합니다.
2. 함수 지역은 저장소에 이미 있는 `vercel.json`의 `regions: ["icn1"]`(서울)을 그대로 씁니다 — Supabase 프로젝트도 서울(`ap-northeast-2`)에 둬서 지연을 줄입니다.
3. **환경 변수 `ENABLE_EXPERIMENTAL_COREPACK=1`을 반드시 넣습니다.** Vercel은 기본으로 lockfile 버전(`lockfileVersion 9.0`)만 보고 pnpm 9 또는 10을 고르는데(vercel.com/docs/package-managers), 이 저장소는 `package.json`의 `packageManager`가 `pnpm@11.8.0`이고 `pnpm-workspace.yaml`의 `allowBuilds`(onnxruntime-node·sharp 등 설치 스크립트를 꺼서 안 쓰는 네이티브 의존성이 빌드되지 않게 함)와 `minimumReleaseAgeExclude`가 pnpm 11 전용 설정이라, Corepack으로 `packageManager`가 가리키는 버전을 그대로 써야 합니다. 이 변수 없이 배포하면 pnpm이 다른 버전으로 설치되어 위 설정이 무시되거나 설치가 실패할 수 있습니다.
4. Vercel 프로젝트 설정의 Node 버전은 **24.x**로 맞춥니다(kordoc은 Node 20 이상이 필요하지만, 이 앱 자체가 Node 24 기준으로 작성됨 — `CLAUDE.md` 첫머리).
5. 운영에 넣을 환경 변수는 `.env.example`의 「운영(Vercel)에 넣는 변수」 절 이름 그대로 넣습니다(값은 이 문서에 적지 않음): `NEXT_PUBLIC_SUPABASE_URL`·`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`·`SUPABASE_SECRET_KEY`·`NEXT_PUBLIC_SITE_URL`(운영 도메인)·`ALLOWED_EMAIL_DOMAINS`(기본 `kca.kr`)·`AI_PROVIDER=api`·`ANTHROPIC_API_KEY`·`ANTHROPIC_API_KEY_FALLBACK`(선택, 예비 키)·`CRON_SECRET`(과제 매칭 처리기 — `/api/prep/run`)·모델·effort를 바꿀 때만 `CLAUDE_MODEL_HEAVY`·`CLAUDE_EFFORT_HEAVY`·`CLAUDE_MODEL_LIGHT`·`CLAUDE_EFFORT_LIGHT`(비우면 두 등급 `claude-sonnet-5-5`, effort는 기능별 표 `lib/ai/models.ts`)·`PREP_AUTORUN`(선택, `off`면 자동 매칭 끔). `SUPABASE_DB_URL`·`CLAUDE_CLI_*`·`DB_TARGET`은 로컬·스크립트 전용이라 Vercel에 넣지 않습니다.
6. Vercel 프로젝트의 지출 한도(Spend Management)를 켜서 예상치 못한 과금을 막습니다.

**kordoc이 Vercel 함수 안에서 그대로 도는 이유**(배포 전 이해할 것): kordoc(4.15.3, npm 공식 저장소, MIT)은 앱이 쓰는 HWP·HWPX·PDF(`pdfjs-dist`)·워드·엑셀 글 읽기와 HWPX 쓰기를 순수 JS로 합니다. 네이티브 선택 의존성(`sharp`·`onnxruntime-node`·`@hyzyla/pdfium`·`@huggingface/transformers`·`puppeteer-core`)은 OCR·그림 변환 때만 동적으로 불러오고, `next.config.ts`의 `outputFileTracingExcludes`로 함수 묶음에서 빠집니다(`pdfjs-dist`의 `@napi-rs/canvas`도 함수 묶음에 안 실리지만 글 읽기에는 필요 없음). 로컬에서 이 모듈들을 모두 막고 2025 경영실적보고서 PDF(31.9만 자)·카드 HWP·HWPX를 읽어 막지 않았을 때와 글자 수까지 같음을 확인했습니다. kordoc을 쓰는 함수 묶음 크기는 14~17MB(Vercel 한도 250MB)입니다. 글자 없는 스캔 PDF는 OCR을 안 쓰므로 거절합니다(지금 앱 동작 그대로, 운영에서도 바뀌지 않음).

**pdca-app만 배포해도 됩니다**: 실행 중 외부 의존은 Supabase(DB·저장소·인증)와 Claude API뿐입니다. `../pdca`·report-harness(로컬 `pnpm harness:sync` 스크립트에서만 씀)·Claude Code CLI(로컬 전용 — Vercel은 항상 `api` 경로)·`resources/knowledge`·`data/`(적재·테스트 스크립트에서만 읽음, 앱은 DB·저장소에서 읽음)·파이썬(초기 변환 스크립트, 참고용 — 2026-09-28에 지움, git 이력에만)은 운영 실행에 필요 없습니다.

## 2. Supabase

**누가**: 관리자.

1. 운영 프로젝트를 서울 리전(`ap-northeast-2`)에 만듭니다.
2. 마이그레이션 적용: `.env.local`(또는 CI 환경)에 `SUPABASE_DB_URL`(Session pooler 주소)을 넣고 `pnpm db:push`.
3. **로그인 메일 SMTP 연결은 필수입니다.** Supabase 기본 메일(built-in)은 시간당 2통까지만 보내고 프로젝트 팀원 주소로만 갑니다(supabase.com/docs/guides/auth/rate-limits, auth-smtp 문서) — 기관 구성원 전체가 로그인할 수 없습니다. 운영 전에 반드시 SMTP를 연결합니다.
   - **지금 설정(2026-10-26)**: 운영 발송용 Gmail 계정(2단계 인증 + 앱 비밀번호, 주소는 Supabase SMTP 설정에 있음) → `smtp.gmail.com:465`, 발신자 이름 「경영평가 Sherpa」(2026-10-27 서비스 이름이 「경평AI비서」로 바뀜 — Supabase SMTP 설정의 발신자 이름도 바꿀 것), 시간당 발송 한도 60통(Authentication → Rate Limits). 관리 API(`PATCH /v1/projects/<ref>/config/auth`, 개인 액세스 토큰 `sbp_…`)로 넣었고 앱 비밀번호는 Supabase에만 둠(`.env.local`의 `GMAIL_APP_PASSWORD`는 로컬 시험용).
   - 기관 SMTP 릴레이(25번 포트, IP 인증만 — 접속 정보는 공개 저장소에 적지 않음)는 쓰지 못함: Vercel 함수(AWS 서울)는 25번 포트로 나가는 연결이 막혀 있고(Gmail 수신 서버 25번도 시간 초과, 587·465는 됨 — 2026-10-26 실측) 출발 IP도 고정이 아님. 기관망 PC에서는 발송됨.
   - 개인 Gmail은 하루 약 500명 수신 한도(업체 자료 기준). 넘으면 최대 24시간 발송이 멈추고, 앱 비밀번호가 새면 Google 계정에서 폐기·재발급한 뒤 Supabase SMTP 비밀번호를 바꿈.
4. Auth 설정(Authentication → URL Configuration)의 **Site URL**을 운영 주소(`https://kca-sherpa.vercel.app`)로, **Redirect URLs**에 `https://kca-sherpa.vercel.app/**` · `https://kca-sherpa-*-kcaev3-2151.vercel.app/**`(배포·미리보기 주소) · `http://localhost:3000/**`(로컬 개발)를 넣습니다. 앱은 메일 링크가 돌아올 주소를 **호출한 주소 기준**으로 보내므로(`lib/auth/redirect.ts requestOrigin`, 2026-10-12) 이 목록에 있으면 운영·미리보기·로컬이 각자 자기 주소로 돌아옵니다. 목록에 없으면 Supabase가 Site URL(루트)로 `/?code=…`를 붙여 보내는데, 앱이 그것도 `/auth/confirm`으로 넘기지만(`proxy.ts`) Site URL이 다른 주소(예: localhost)면 그 주소로 갑니다(2026-10-12 첫 배포 때 실제로 겪음).
5. 이메일 템플릿이 `token_hash` 변수를 쓰는지 확인합니다(`app/auth/confirm`이 `token_hash`와 `code` 둘 다 받지만, 권장 양식은 `token_hash`). 2026-10-26부터 Magic Link·Confirm signup 두 양식은 한국어이고 링크는 `{{ .RedirectTo }}&token_hash={{ .TokenHash }}&type=email`(앱이 보내는 `emailRedirectTo`에 늘 `?next=`가 있어 `&`로 이음 — 허용 목록에 없는 주소로 요청하면 Site URL로 떨어져 링크가 깨짐).
6. 프로젝트 지출 상한을 설정합니다.
7. 백업 설정(Point-in-Time Recovery 등)을 켭니다.

**새 운영 프로젝트를 처음 채우는 순서**(기존 프로젝트를 재사용하지 않는 경우만):

## 3. Claude API

**누가**: 관리자.

> **지금 운영 방식(2026-10-16 사용자 결정)**: API 크레딧은 충전하지 않고 AI는 **로컬 앱(`./run-app.sh dev`) + Claude Code CLI 경로**(`.env.local` `AI_PROVIDER=cli`)로만 씁니다. 로컬은 모든 AI 호출이 `aiProvider()`(`lib/ai/run.ts`)를 거쳐 CLI로 돌아 크레딧을 쓰지 않고, 그림 설명(첨부 이미지·스캔 PDF)만 CLI가 그림을 못 받아 「보류」로 남습니다. Vercel 운영은 늘 API 경로라 크레딧이 없는 동안 AI 기능이 「크레딧 부족」 안내로 실패합니다(AI 아닌 화면·내려받기는 그대로). `.env.local`의 `AI_PROVIDER`를 비우면 API 키가 있을 때 api로 바뀌므로 `cli`를 지우지 않습니다.

1. Anthropic 콘솔에서 API 키를 발급받아 Vercel `ANTHROPIC_API_KEY`에 넣습니다. 예비로 다른 조직의 키가 있으면 `ANTHROPIC_API_KEY_FALLBACK`에 넣습니다 — 기본 키가 크레딧 부족으로 거절될 때만 같은 요청을 예비 키로 다시 보내고(과금 없는 거절이라 안전, 평소에는 기본 키만 써서 프롬프트 캐시가 유지됨), 둘 다 부족하면 「크레딧 부족」 안내입니다. 크레딧은 조직 단위라 같은 조직의 키는 예비가 되지 못합니다.
2. `AI_PROVIDER=api`. 모델 등급은 비우면 기본값(heavy·light 모두 `claude-sonnet-5-5`, effort는 heavy `xhigh`·light `low` — 2026-09-30 사용자 결정)이고, 바꿀 때만 `CLAUDE_MODEL_HEAVY`·`CLAUDE_EFFORT_HEAVY`·`CLAUDE_MODEL_LIGHT`·`CLAUDE_EFFORT_LIGHT`를 넣습니다. 경평 초안 품질이 Opus 5.5보다 떨어지면 `CLAUDE_MODEL_HEAVY=claude-opus-5-5`로 되돌립니다(API 경로의 `xhigh` 허용 여부는 연기 시험 때 확인 — `xhigh`는 생각 토큰이 늘어 `max_tokens`에서 잘릴 수 있음). 로컬 CLI 경로 별칭은 `CLAUDE_CLI_MODEL_HEAVY`·`CLAUDE_CLI_MODEL_LIGHT`(운영 Vercel에는 필요 없음)이고, 옛 `CLAUDE_MODEL_WRITER`·`CLAUDE_CLI_MODEL`·`CLAUDE_CLI_EFFORT`는 heavy로 읽습니다(`CLAUDE_INSPECT_EFFORT`는 없어짐). 기능별 등급은 `lib/ai/models.ts`의 `FEATURE_TIER`(과제 매칭만 light, 나머지 heavy)이며 effort는 기능별 표 `FEATURE_EFFORT`가 작성지원·질문·코멘트·블록 고치기만 `high`로 낮추고(2026-10-07, 월간 점검·경평 구성안·집필은 `xhigh`), `CLAUDE_EFFORT_HEAVY`를 명시하면 그 값이 전 기능에 앞서므로 품질 문제 시 `CLAUDE_EFFORT_HEAVY=xhigh`로 한 줄에 되돌립니다. 그리고 「AI 사용량」 화면에 등급이 표시됩니다.
3. 콘솔에서 월 지출 한도와 알림을 설정합니다.
4. **API 경로 연기 시험**(2026-09-28 기준 아직 하지 않음 — `.env.local`에 API 키가 없어 CLI 경로로만 검증됨): 배포 전에 `AI_PROVIDER=api`로 `scripts/smoke/`의 7개 기능(작성지원·질문·드래그 코멘트·월간 점검·경평 초안·블록 고치기 등) 연기 시험을 한 번씩 돌려 API 경로가 CLI 경로와 같은 결과를 내는지 확인합니다.
5. 배포 뒤 관리자 「AI 사용량」 화면(`/admin/usage`)에서 호출별 토큰과 추정 금액이 보이는지 확인합니다.

## 4. 개발·운영 DB 분리

- 개발용 Supabase 프로젝트를 따로 두고, 개발 `.env.local`에 `DB_TARGET=development`를 넣습니다.
- `DB_TARGET`이 비어 있으면 `production`으로 취급됩니다(`CLAUDE.md` 「명령」 절 「운영 DB 보호」). `pnpm e2e`·`e2e:ui`·`e2e:shots`·전체 `pnpm db:seed`는 운영 DB에서 실행 전에 멈춥니다.
- 운영 관리 명령(`db:push`·`db:user`·`db:layout`·`knowledge:*`·`harness:sync`·`db:check-search`)과 읽기만 하는 `scripts/smoke/*`·`scripts/eval/*`는 막지 않습니다 — 그래도 운영 DB에서 돌릴 때는 신중히 확인합니다.

- 주관 부서 지정(`eval_units.lead_team_id`)은 성과관리팀이 `/reports`에서 합니다. 사업별 배정 검토는 `docs/analysis/2025-주요사업-공통부분-분석.md`(절 단위 배정 근거)를 참고합니다.

**부서 직접 확정 반영(2026-10-27)**: 새 마이그레이션 둘 `20261027100000`(보낸 점검표 DB 잠금)과 `20261027110000`(부서 직접 확정 — 부서 원장 쓰기 정책·`guard_card`, 작성본 확정 허용, 이력 정책, 보고서 전이 표)이 있어서 위 「코드 먼저 db:push」와 순서가 다릅니다.
1. **Vercel에 새 코드 배포** 먼저.
2. **곧바로 `pnpm db:push`** — 둘이 함께 적용됩니다.
3. 이유: 점검표 잠금은 옛 코드의 보내기 취소(내용도 바꾸는 쓰기)를 거절하므로 새 코드가 먼저여야 하고, 부서 확정은 새 코드가 새 DB를 요구하지만 부서 담당자 쪽은 아직 열지 않아 배포와 `db:push` 사이 몇 분은 무해합니다.
4. 점검: 시험 부서 계정으로 카드 하나를 「확정(원장 반영)」 → 성과관리팀 계정으로 수정 이력(`card_edits`)과 원장 내용 확인 → 원장을 이전 내용으로 되돌림.
5. 되돌리기(down)는 마이그레이션 머리 주석에 있음. 부서가 확정한 작성본·이력·원장 내용은 지우지 않음.

## 8. 참고자료 3단계 적용(2026-09-30)

과제 대응표·공통 지식 매칭 처리기의 운영 적용 사항입니다(설계는 `docs/design/knowledge.md` 「과제 대응표와 준비물 처리기」, 진행은 `docs/plan/참고자료-진행현황.md`). 코드는 커밋·푸시했으나(`c7dfa69`) 아직 배포하지 않았습니다 — 이 계정에 Vercel 프로젝트가 없어 §1부터 만들어야 합니다.

1. **마이그레이션 셋은 운영 DB에 적용돼 있습니다**: `20260930090000_prep_tables.sql`(새 표 넷 `card_knowledge_scope`·`report_material_cards`·`card_context_manifest`·`prep_jobs`, 옛 지적 연결 이관, `ai_requests.user_id` null 허용·`job_id`), `20260930100000_material_cards_candidate.sql`(추가자료 연결 상태에 `candidate` 허용). 새 운영 프로젝트를 처음 채울 때는 `pnpm db:push`가 함께 적용합니다. 3-5 재정의로 안 쓰게 된 것은 세 번째 마이그레이션 `20260930110000_prep_cleanup.sql`(2026-09-30 운영 적용)이 걷어냈습니다 — `card_context_manifest` 표 삭제(0행), `report_material_cards.status`는 `confirmed`만(기본값도), `prep_jobs.kind`는 `match_knowledge`만, `private.can_enqueue_prep`의 자료 매칭 분기 삭제. 지운 행은 없었습니다(운영에서 사전 확인).
2. **환경변수**(`.env.example`의 해당 절 참고): 
   - `CRON_SECRET` — `/api/prep/run` 인증(`Authorization: Bearer <값>`). 비우면 라우트는 늘 401.
   - `PREP_AUTORUN` — 비우면 Vercel은 자동 처리(공통 지식 매칭)·로컬은 없음. `all`=로컬도 자동, `off`=어디서나 자동 처리 없음(수동). 지금은 비워 둠(Vercel 자동 — 아래 4번).
   - `CLAUDE_MODEL_LIGHT` — 매칭용 light 모델(비우면 `claude-sonnet-5-5`).
   - `CLAUDE_CLI_MODEL_LIGHT` — 로컬 CLI 경로용 별칭(비우면 `sonnet`, 운영 Vercel에는 필요 없음).
3. **크론은 아직 설정하지 않았습니다.** `vercel.json`에 크론을 넣기 전에 Vercel 공식 문서(요금제별 주기 제한)를 확인합니다(결정 P8). 라우트는 안전망이라 크론 없이도 안전합니다(비밀이 없으면 늘 401).
4. **배포하면 Vercel에서는 카드 저장 때 `after()`로 공통 지식 매칭이 자동으로 돕니다(2026-09-30 사용자 결정 — 자동으로 둠).** 과제 정체성(과제명·실행과제·대상사업·계량지표 이름)이 바뀐 저장, 새 카드·되살림에서만 등록되고 light 모델(`claude-sonnet-5-5`·effort low)을 부릅니다. 카드 한 장 약 45만 토큰(2026-09-29 표본 실측, 호출 2회·13~16초). 저장할 때마다 토큰이 나가므로 사용량은 관리자 「AI 사용량」(feature `prep_match`)에서 보고, 끄려면 Vercel 환경변수에 `PREP_AUTORUN=off`(그러면 아래 5번대로 수동 처리).
5. **첫 매칭·다시 매칭**은 `pnpm prep enqueue --match [--business BZ-1] [--card <id>] [--doc <문서 id>] [--dry-run]`로 작업을 등록한 뒤 `pnpm prep run --ai`로 처리합니다. 운영 DB를 가리키므로 건수를 확인하고 승인을 받은 뒤 돌립니다(59장 전체는 호출 118회·입력 약 1,330만 토큰 어림). 사람이 확정·뺀 대응은 다시 매칭해도 덮지 않습니다.
6. **처리 확인**은 `pnpm prep status`(종류·상태별 건수)입니다. 실패한 작업은 `prep_jobs`의 오류 칸과 관리자 「AI 사용량」(feature `prep_match`)에서 봅니다.

## 9. 일반 문서 올리기(참고자료 5단계, 2026-09-30)

공통 지식에 새 문서를 화면에서 올리는 절차입니다(설계는 `docs/design/knowledge.md` 「일반 문서 올리기와 적재 통일」). 아직 배포 전이라 화면 업로드는 운영에서 시험하지 못했습니다(실제 환경 왕복 시험 한 번만 통과).

1. **어디서·누가**: 「관리 › 공통 자료·틀」 화면, 관리자만.
2. **파일**: kordoc이 읽는 형식, 파일 100MB 한도. 30MB를 넘는 큰 파일은 CLI(`pnpm knowledge:add <파일> --title "제목" --scope <범위> [--year] [--edition] [--issuer] [--dry-run]`)를 권장합니다(서버 함수 안 읽기 시간은 못 쟀고, 이 컴퓨터에서 476쪽 48.7MB를 11.5초에 읽음). 글이 200자 미만인 스캔 문서는 거절됩니다(OCR은 4단계).
3. **범위와 영향**: 올릴 때 기관 공통·공통지표·가점·주요사업 1·2·3 공통·검색 전용 중 고릅니다. 검색 전용이 아니면 그 범위의 모든 AI 요청 앞에 글 전체가 들어갑니다. 사업별 공유 층 글자 수가 **40만 자**(`SHARED_CHARS_LIMIT`)를 넘게 되면 저장하지 않고 「검색 전용으로 올리거나 범위를 줄이라」고 안내합니다. 2026-09-30 기준 여유는 BZ-1 약 10.9만·BZ-2 약 7.0만·BZ-3 약 9.1만 자입니다.
4. **올린 뒤**: 검색 전용이 아니고 매칭 대상 조각이 있으면 닿는 사업의 활성 카드에 매칭 작업이 등록됩니다. Vercel에서는 자동 처리되고(§8 4번), 크론은 없으므로 남는 작업은 `pnpm prep run --ai`로 처리합니다.
5. **함수 최대 시간**: 화면 업로드 때 서버 함수 최대 시간은 300초(`maxDuration`)입니다. 큰 문서의 읽기 시간은 배포 뒤 실측이 필요합니다(확인 필요).
6. **실패하면**: 읽기·검산·크기 보호 중 하나라도 실패하면 DB에 아무것도 남지 않고 저장소 파일도 지워집니다.
7. **삭제**: 화면에서 일반 문서(id `up-…`)만 지울 수 있고, 그 문서의 조각과 과제 대응표 행(사람이 확정한 것 포함)이 함께 사라집니다.

### P0-1 로그인 뒤 이동 주소 열린 리다이렉트(확인)
- **문제**: `lib/auth/redirect.ts` `safeNext`가 `/`·`//`·`/\`·`\r\n`만 거르고 탭 같은 제어 문자를 거르지 않음. `"/\t/evil.com"`이 통과하는데 URL 해석에서 탭이 지워져 `https://evil.com/`이 됨(`new URL("/\t/evil.com", base)`로 직접 확인). `next=`가 든 로그인 링크로 로그인 직후 외부로 보낼 수 있음(`app/auth/confirm/actions.ts:39` `redirect(next)`, 같은 함수 `app/login/actions.ts:21`·`app/auth/confirm/page.tsx:14`).
- **설계**: `safeNext`가 `lib/nav/return-to.ts` `safeReturn`과 같은 규칙을 쓰게 함 — 제어 문자(`\u0000-\u001f\u007f`) 거부, `/스킴:` 거부, 길이 상한. 두 함수가 한 검사 함수(`isSafeAppPath`)를 공유(규칙 한 곳).
- **파일**: `lib/auth/redirect.ts`, `lib/nav/return-to.ts`(공유 함수로 옮기기만), `lib/auth/redirect.test.ts`.
- **시험**: `"/\t/evil.com"`·`"/\n/evil.com"`·`"/\u0000x"`·`"/javascript:alert(1)"` → 기본 경로, `"/cards?x=1"` 그대로. 기존 사례 통과.

### P0-2 AI 집필·구성안 저장에 버전 확인(확인)
- **문제**: 과제별 초안 쓰기 7곳이 버전 확인 없이 덮어씀 — 집필 `writeDraft`·`writeMgDraft`(`app/(app)/reports/cards/actions.ts:301·369` `upsert(onConflict card_id,year)`), 구성안 만들기(`:428·473` upsert), 구성안 고치기(`saveReportOutline`·`saveMgOutline` `:526·543`), BP 표시(`:76`), 구성안 승인(`approveReportOutline`). 집필은 5~12분 걸려 그 사이 사람이 「직접 고치기」로 고친 글을 AI 결과가 지움. 블록 고치기·직접 고치기·되돌리기는 이미 `updated_at` 조건이 있음(`:621-640`).
- **설계**:
  - `prepareDraft`가 시작할 때 이 과제·연도의 `card_report_drafts.updated_at`(없으면 null)을 읽어 `Prepared.base`에 둠.
  - 공용 저장 함수 `saveDraftRow(supabase, { cardId, year }, row, base)` — base가 있으면 `update(row).eq(card_id).eq(year).eq("updated_at", base).select("updated_at")`, 0행이면 충돌. base가 null이면 `insert(row)`, 유일 위반(23505)이면 충돌. 성공하면 새 `updated_at`을 돌려줌(B2a의 2차 저장에 씀).
  - 7곳 모두 이 함수로(주요사업·경영관리 쌍의 중복이 같이 줄어듦). 사람이 고치는 액션(구성안 고치기·BP·승인)은 같은 요청에서 읽은 `updated_at`을 base로.
  - 충돌이면 `{ ok: false, conflict: true, message: "AI가 쓰는 동안 이 과제의 초안(구성안)이 바뀌었습니다 — 새 결과는 저장하지 않았습니다. 화면을 새로 고친 뒤 다시 만들어 주세요." }`(D6 기본안 — AI 결과를 버림, 충돌은 드묾).
- **파일**: `app/(app)/reports/cards/actions.ts`, 새 `lib/reports/draft-store.ts`(저장 함수 — 순수에 가깝게 클라이언트를 인자로), 화면 안내는 기존 오류 줄 그대로.
- **시험**: `draft-store.test.ts` — 가짜 클라이언트로 ① base 일치 → 저장·새 버전 ② base 불일치(0행) → conflict ③ base null + 행 있음(23505) → conflict ④ base null + 행 없음 → insert. 연기 시험: 로컬에서 집필 중 직접 고치기 → 집필 결과가 충돌로 끝나는지(수동 확인 기록).
- **위험**: 버전을 잘못 넘기면 모든 저장이 충돌 — 시험 ①로 막음.

### P0-3 AI 호출 기록·제한 공용 래퍼(확인) — 병목 측정 B1 포함
- **문제**:
  - 1분 5회 제한이 `ai_requests`의 최근 60초 행을 세는데, 행은 AI가 끝난 뒤에 넣음(`app/(app)/cards/actions.ts:165`→`:212`, `inspections/actions.ts:128`→`:159`, `reports/cards/actions.ts:163`→`:299` 등). 5~10분짜리 호출이 도는 동안은 하나도 안 세져 사실상 제한이 없음.
  - 함수가 끊기면(Vercel `maxDuration`) 성공·실패 어느 행도 안 남아 쓴 토큰이 비용 집계에서 빠짐. AI는 성공했는데 그 뒤 검증이 예외를 던지면 토큰 없는 `error` 행만 남음(`cards/actions.ts:225`, `inspections/actions.ts:188`). insert 결과를 확인하지 않음.
  - 같은 「제한 확인 → 호출 → 기록」 덩어리가 16곳(insert)·4곳(count)에 복사돼 있음.
  - **병목 측정 불가**: 소요 시간 열이 없어 운영에서 어느 단계가 느린지 모름.
- **설계**:
  - 마이그레이션 `ai_requests`: `status` 허용값에 `running` 추가, 열 `finished_at timestamptz`·`duration_ms integer`·`timings jsonb`(단계별 ms: `prepare`·`call`·`verify`·`fix`·`save`). 로그인 사용자에게 **열 단위** update 권한(status·model·토큰 열·error·finished_at·duration_ms·timings만)과 정책 `using (user_id = auth.uid() and status = 'running') with check (user_id = auth.uid())` — 끝난 행·남의 행은 못 고침.
  - 래퍼 `lib/ai/request-log.ts`(server-only): `startAiRequest(supabase, { userId, cardId, feature, mode, limited })` → ① 이 사용자의 20분 넘은 `running` 행을 `error`(「중단 — 시간 초과 추정」)로 닫음 ② 제한: 최근 60초 행(상태 무관) < 5 **그리고** 진행 중(`running`, 20분 안) < 2(일괄 점검 동시 2건 — B5와 맞춤) ③ `running` 행을 넣고 id 반환. `finishAiRequest(id, { status, model, usage, error, timings })`. AI 호출이 돌려준 사용량은 검증 전에 기록(검증 예외에도 토큰이 남음).
  - 16곳을 래퍼로 교체, count 질의 4곳 삭제. 첨부 그림 설명(`lib/ai/attachments.ts`)은 `limited: false`. 처리기(서비스 키, `job_id`)는 지금처럼 insert만 하되 `duration_ms`는 채움.
  - AI 사용량 화면(`app/(app)/admin/usage/page.tsx`): `running`·중단 표시, 기능별 소요 시간 중앙값 열.
- **파일**: `supabase/migrations/2026101xxxxxxx_ai_requests_running.sql`, `lib/ai/request-log.ts`, `app/(app)/cards/actions.ts`, `app/(app)/inspections/actions.ts`, `app/(app)/reports/cards/actions.ts`, `lib/ai/attachments.ts`, `app/(app)/admin/usage/page.tsx`.
- **시험**: `migrations.test.ts` — 자기 `running` 행 끝내기 됨 / 남의 행·끝난 행 고치기 안 됨 / `user_id`·`feature` 열 update 안 됨. `request-log.test.ts`(가짜 클라이언트) — 진행 중 2건이면 거절, 60초 5건이면 거절, 오래된 running 정리, 검증 전 사용량 기록 순서.

### P0-4 과제 매칭 처리기 무한 재실행(확인)
- **문제**: `lib/prep/store.ts:46-57` `reclaimStuck`가 15분 넘게 `running`인 작업을 시도 횟수와 상관없이 `queued`로 되돌림. `MAX_ATTEMPTS = 2`(`lib/prep/queue.ts:8`)는 처리기가 예외를 던질 때만 적용 — 함수 시간 초과로 통째로 죽는 작업은 끝없이 다시 돌아 AI 비용이 반복됨(추정 경로지만 코드 흐름은 확인).
- **설계**: `queue.ts`에 순수 `reclaimState(attempts) → "queued" | "failed"`(= `stateAfterError`와 같은 규칙), `reclaimStuck`가 `attempts`를 읽어 상한이면 `failed`(「시간 초과로 N번 멈춤」).
- **파일**: `lib/prep/queue.ts`, `lib/prep/store.ts`, `lib/prep/queue.test.ts`·`run.test.ts`.
- **시험**: 시도 1회 멈춤 → queued, 2회 → failed.

### B2a·b·d 집필: 1차 초안 먼저 저장 · 시간 예산 · 문장만이면 고치기 안 함(병목 — 확인)
- **문제(실측)**: 집필 28건 모두 자동 고치기를 한 번 더 돌림(첫 초안 판면 68~118%, 26건이 95~102% 밖). 집필 중앙 490초·최대 744초로 Vercel `maxDuration` 800초에 가깝고, 1차 초안을 저장하지 않아 고치기 도중 끊기면 두 호출분을 모두 잃음. `AGAIN_BEFORE_MS`(170초)는 세 번째 호출만 막고 두 번째는 시간과 무관하게 돎(`lib/ai/run.ts` `callReportSectionFitted`).
- **설계**:
  - (a) 1차 초안이 나오면 바로 저장(P0-2 `saveDraftRow`, 경고에 「자동 고치기 중」 없이 그대로) → 고친 판이 더 좋으면 같은 함수로 갱신(base = 1차 저장이 돌려준 버전). 화면은 지금처럼 끝난 뒤 새로 고침.
  - (b) `callReportSectionFitted`에 `deadlineMs`(기본 700초 — 800초에서 여유) 옵션: 남은 시간 < 1차 호출에 걸린 시간 × 1.1이면 고치기를 건너뛰고 경고 「시간이 모자라 자동 고치기를 하지 않았습니다 — 「다시 만들기」나 블록 고치기로 고쳐 주세요」.
  - (d) 고치기 조건에서 「문장 문제만」은 뺌(28건 중 2건 — 경고로만 남김).
- **파일**: `lib/ai/run.ts`, `app/(app)/reports/cards/actions.ts`, `lib/ai/progress.ts`(진행 줄 문구가 실제와 같게).
- **시험**: `run.ts` 고치기 판단을 순수 함수(`shouldFix(check, elapsedMs, firstMs, deadlineMs)`)로 빼서 시험 — 판면만·문장만·시간 부족 사례. 로컬 CLI 집필 1건으로 1차 저장 → 2차 갱신 확인(`timings`에 `call`·`fix` 기록).

## 4. P1 — 규칙 일관성·운영 안정

### P1-1 보고서 상태 전이 표 + 현재 상태 조건 + DB 가드(확인)
- **문제**: `setReportStatus`(`app/(app)/reports/actions.ts:64-92`)는 부서만 `deptCanMove`로 검사하고 성과관리팀은 아무 전이나 가능(준비 → 승인, 제출 조건 무시). 쓰기에 현재 상태 조건이 없어(`update(patch).eq("id", id)`) 동시 변경이 경쟁함. DB `guard_report`(`20260927170000_report_dept_submit.sql:87`)는 부서의 승인·식별값만 막음. 화면이 성과관리팀에게 여는 전이는 「돌려보내기(제출 → 작성 중)」·「승인(제출 → 승인)」뿐(`components/reports/report-controls.tsx:191·220`).
- **설계**:
  - `lib/reports/model.ts`에 전이 표 하나 `canMove(role, from, to)`: 부서 = 준비→작성 중·작성 중→제출·제출→작성 중, 성과관리팀 = 부서 전이 + 제출→승인·제출→작성 중(메모 필수 — 기존 규칙). 그 밖은 거절. 원고 첫 저장의 준비→작성 중(`actions.ts:311`)도 이 표로.
  - `setReportStatus`: `canMove` 검사, `update(...).eq("id", id).eq("status", report.status)` → 0행이면 「다른 사람이 먼저 상태를 바꿨습니다 — 새로 고침」.
  - DB: `guard_report`에 상태 전이 검사를 역할 무관하게 추가(`private.report_transition_ok(old, new, is_staff)` — TS 표와 같은 목록, 서비스 키는 통과).
- **파일**: `lib/reports/model.ts`, `app/(app)/reports/actions.ts`, 새 마이그레이션(트리거 교체), `components/reports/report-controls.tsx`(버튼 노출을 `canMove`로 — 화면·서버 같은 규칙).
- **시험**: `model.test.ts` 전이 표 전수, `migrations.test.ts` — 성과관리팀 준비→승인 거절·제출→승인 됨, 부서 제출→승인 거절, 같은 행을 두 번 바꾸면 두 번째가 0행.

### P1-2 점검표 보낸 뒤·확인 뒤 잠금(확인)
- **문제**: `saveInspection`(`app/(app)/inspections/actions.ts:51-70`)은 `acknowledged`만 막고, `sent`에서 `intent: "save"`면 상태가 조용히 `draft`로 돌아감(부서 화면에서 사라짐). 화면은 보낸 뒤 편집을 숨기지만(`components/inspections/inspection-editor.tsx:90`) 서버는 막지 않음. DB `guard_inspection_ack`는 성과관리팀에게 걸리지 않아 확인된 점검표도 고칠 수 있음.
- **설계**: 서버 — `sent`이면 `unsend`만 허용(「보낸 점검표는 보내기를 취소한 뒤 고칠 수 있습니다」), `acknowledged`는 모두 거절(지금처럼). DB — `guard_inspection_ack`에 「`old.status = 'acknowledged'`면 로그인 사용자(성과관리팀 포함) 누구도 내용·상태를 못 바꿈」 추가(서비스 키 통과).
- **파일**: `app/(app)/inspections/actions.ts`, 새 마이그레이션(P1-1과 같은 파일로 묶어도 됨).
- **시험**: `migrations.test.ts` — 성과관리팀이 acknowledged 행 update 거절. 서버 판단을 순수 함수(`inspectionWriteAllowed(status, intent)`)로 빼서 시험.

### P1-3 API 스트림 실패 처리·오류 구분 + API 경로 실호출 검증(크레딧 필요)
- **문제(확인+추정)**: `structuredApi`(`lib/ai/run.ts:102-127`)는 SDK 기본(재시도 2회, 스트림 시작 전 오류만)이고, 스트림 도중 과부하·연결 끊김이면 5~10분·출력 5~7만 토큰을 통째로 잃음. `aiErrorMessage`(`run.ts:643`)가 429·529·시간 초과·연결 오류를 뭉뚱그림(추정). SDK 클라이언트 시간 제한을 명시하지 않음(추정 — 기본값과 긴 스트림의 관계는 실측 필요). Vercel은 늘 API 경로인데 실제 API 호출은 아직 한 번도 못 해 봄.
- **설계**: ① 클라이언트를 `new Anthropic({ timeout: 기능별 상한(예: 15분), maxRetries: 2 })`로 명시 ② 스트림 도중 실패는 「첫 60초 안이거나 과부하(529·overloaded_error)」일 때만 한 번 더(그 뒤는 비용이 커서 재시도하지 않고 안내) ③ `aiErrorMessage`를 오류 종류별 문구로(속도 제한 → 1분 뒤 / 과부하 → 잠시 뒤 / 시간 초과 → 다시 만들기·요청 좁히기 / 연결 → 다시 시도) ④ API 연기 시험 4종(작성지원·월간 점검·구성안·집필)을 크레딧 확보 뒤 돌려 출력 속도·캐시 읽기/쓰기·시간을 `docs/design/ai-assist.md`에 기록(B3·B4·B6의 기준값).
- **파일**: `lib/ai/run.ts`, `lib/ai/run`의 오류 문구 시험, `scripts/smoke/*`(이미 있는 것에 `AI_PROVIDER=api` 옵션 확인).
- **시험**: 오류 분류를 순수 함수로 빼서 시험(SDK 오류 객체 모양별). 연기 시험은 크레딧 뒤.

### P1-4 개발 DB — **D2 결정 필요**

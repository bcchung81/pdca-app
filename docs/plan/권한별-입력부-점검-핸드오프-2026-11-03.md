# 권한별 화면 입력부 점검 핸드오프(2026-11-03)

- 작성일: 2026-11-03
- 대상: 권한·DB·서버 액션을 이어서 고칠 개발 담당자(다음 세션의 Claude Code 포함)
- 상태: 2026-11-03 같은 날 §5의 1~5번과 6번 중 2곳을 고침(미커밋·운영 미반영 — §8). 6번 셋째(주관 부서 확정 안내)와 §7-5 쓰지 않는 코드는 그대로.
- 요청: 「현재 프로젝트의 화면 입력부를 각 권한별 담당자 구분으로 확인」

화면에서 사용자가 쓰기를 일으키는 곳(입력칸·단추·파일 올리기 → 서버 액션)을 역할 셋(부서 담당자·성과관리팀·관리자)으로 나눠 정리했다. 그리고 「화면 노출 조건 ↔ 서버 액션 역할 검사 ↔ DB(RLS·트리거)」가 서로 맞는지 대조했다. 이전 점검인 `docs/plan/입력필수-점검-2026-10-27.md`는 「무엇을 꼭 넣어야 하나」를 봤고, 이번 점검은 「누가 넣을 수 있나」를 봤다.

## 1. 결론

| 대조 항목 | 결과 |
|---|---|
| 화면 접근 막기 | 정상. 권한이 필요한 화면은 모두 `requireAtLeast`(`NoAccess`)로 막는다. 막기가 없는 3곳(`admin/users`, `cards/[uid]/report`·`report/html`)은 옛 주소를 이어 주기만 하고, `api/prep/run`은 `CRON_SECRET`으로 막는다 |
| 화면엔 있는데 서버가 거절하는 단추 | 없음 |
| 부서 화면 보기(`?team=`)에서 입력칸이 그려지는 곳 | 없음 |
| 로그인 확인 없이 쓰는 서버 액션 | 없음 |
| 서비스 키를 역할 확인보다 먼저 쓰는 곳 | 없음(`users/actions.ts`는 `requireAtLeast` 뒤에 Auth 관리 API에만 씀) |
| **문제** | 중간 3건, 낮음 3건(§5) |

가장 먼저 볼 것은 §5의 1번이다. 부서 「확정」 전의 초안 점검이 확정하는 사람의 담당 과제만 센다. 그래서 동료가 맡은 과제의 초안이 없어도 팀 보고서 전체가 확정·잠길 수 있다.

## 2. 조사 범위와 한계

- 방법: 코드 정적 조사. 서버 액션 파일 17개, 관련 화면·부품, `supabase/migrations/`의 RLS·트리거를 영역 셋(카드 / 경평 초안 / 점검·사용자·지식·관리·로그인)으로 나눠 읽었다.
- 무거운 주장은 메인 세션이 코드·마이그레이션을 직접 열어 다시 확인했다. 아래 표에서 「확인」은 직접 읽은 것이고, 「추정」은 코드 흐름으로 짐작한 것이다.
- **하지 않은 것**
  - 실제 화면 실행. e2e는 운영 DB 보호(`DB_TARGET`)로 막힌다.
  - 운영 DB에서 재현.
  - 운영 DB에 마이그레이션이 실제로 적용됐는지 대조. 10-27 기록상 `pnpm db:push --dry-run`은 「up to date」였다.
- 읽지 않은 본문: `regenerateMgPart`·`runOutlineAlternatives`·`adoptOutlineAlternative`(시그니처와 `previewWriteBlocked`만 확인), `lib/cards/confirm.ts mergeIntoLedger`, `components/cards/review/use-card-review.ts`.

## 3. 권한 모델 요약(이번 점검의 기준)

- 역할 계층: `dept_user` < `pmo` < `admin`(`lib/auth/access.ts atLeast`). 윗 역할은 아랫 역할의 화면을 다 본다.
- **카드 접근은 담당자 지정 기준**이다(`20261001100000_assignee_access.sql`). 부서 담당자는 `card_assignees`에 지정된 활성 카드만 읽고 쓴다(`can_read_card`·`can_write_card`). 같은 팀이어도 예외가 없다. 성과관리팀·관리자는 전체다.
- **보고서·추가자료·검토 코멘트는 팀 단위**다(`can_read_report`·`can_write_report`, 의도된 설계).
- 부서 화면 보기: 성과관리팀·관리자가 `/my…`, `/cards/<uid>`, `/reports/cards/<uid>`, `/reports/<숫자>`를 `?team=`으로 열면 읽기 전용이다(`lib/auth/scope.ts deptScope`).
  - 서버 쓰기 액션은 맨 앞에서 `previewWriteBlocked`를 부른다.
  - 이 장치는 **Referer만 본다.** Referer가 없으면 막지 않는다(`lib/auth/preview.ts` 주석). 권한 장치가 아니라 실수를 막는 이중 장치다. 최종 권한은 RLS다.
- 부서 직접 확정(2026-10-27 사용자 결정, `20261027110000_dept_confirm.sql`): 부서 담당자도 자기 담당 카드의 원장 내용과 보고서 확정·확정 취소를 직접 한다.

## 5. 문제 목록(심각도순)

### 1. [중간] 부서 「확정」 점검이 확정하는 사람의 담당 과제만 센다 — 확인(구조), 실제 발생은 미확인

- 흐름
  - `setReportStatus`는 확정(작성 중→승인) 전에 `loadSubmitCards`로 그 평가단위·팀의 과제를 읽는다. 그다음 `submitReadiness`로 초안이 다 있는지 본다(`app/(app)/reports/actions.ts:105-109`).
  - 이때 쓰는 클라이언트가 사용자 권한이다(`lib/reports/queries.ts:214-220`). 부서 담당자에게는 `cards` RLS가 **지정 과제만** 돌려준다.
  - 그런데 확정은 팀 단위다(`can_write_report`). 확정하면 `private.report_locked`가 그 평가단위 × 팀의 **모든** 과제 초안을 잠근다(`20260927170000_report_dept_submit.sql:7-20`).
- 결과: 한 평가단위의 과제를 같은 팀 두 사람이 나눠 맡은 경우를 보자.
  - A가 자기 과제 초안만 끝내고 「확정」하면, B 과제의 초안이 없어도 점검을 통과한다. 보고서는 승인 상태가 되고 B는 초안을 못 고친다.
  - 지정이 0건인 사람은 total 0이라 `ready=false`로 막힌다.
  - `/my/report` 화면의 「확정 가능」 표시도 같은 함수 기준이라 같은 착시가 있을 것으로 추정한다.
- DB 보강 없음: `guard_report`는 drafting→approved 때 승인자 = 본인만 본다(`20261027110000_dept_confirm.sql:163-166`). 초안 유무는 보지 않는다.
- 고치는 방향(후보, 미결정)
  - (가) `security definer` DB 함수로 그 평가단위 × 팀의 과제·초안 유무 집계를 돌려주고, 서버의 확정 점검이 그것을 쓴다. 서비스 키는 쓰지 않는다(CLAUDE.md: 서비스 키는 Auth 관리 API만).
  - (나) 확정하는 사람이 그 평가단위 × 팀 과제를 다 보지 못하면(지정 안 된 과제가 있으면) 확정을 막고 「동료 담당 과제가 있음」이라고 알린다. 이것도 (가)와 같은 집계 함수가 필요하다.
  - 화면 「확정 가능」 표시도 같은 값으로 맞춘다.
- 먼저 할 일: 운영 DB에서 읽기 전용 조회로 「한 평가단위 × 팀의 활성 과제를 둘 이상의 담당자가 나눠 맡은 경우」가 있는지 확인한다(사용자 승인 뒤).

### 2. [중간] 공통 지식 쓰기는 화면·서버는 관리자만, DB는 성과관리팀까지 — 확인

- 화면 `/admin/library`는 `requireAtLeast("admin")`, 서버 액션도 `admin`이다(`knowledge-actions.ts:36,49,124`, `admin/library/actions.ts:25,82`).
- DB 쪽은 더 넓다.
  - `knowledge_documents_write`·`knowledge_chunks_write`는 `private.is_staff()`다(`20260925090200_rls.sql:202,204`).
  - 저장소 `knowledge_objects_write`도 staff다(`20260925090300_storage.sql:33`).
  - 그 뒤 마이그레이션에서 바뀐 적이 없다(grep으로 확인).
- 결과: 성과관리팀이 자기 로그인 토큰으로 Supabase API를 직접 부르면 일반 문서·붙임2 조각을 넣거나 지울 수 있다(추정, 호출은 해 보지 않음).
- 고치는 방향: 세 정책을 `private.is_admin()`으로 좁히는 마이그레이션(`is_admin`은 `rls.sql:37`에 있음). `lib/db/migrations.test.ts`에 성과관리팀 거절 사례를 더한다.
- 영향 확인
  - `pnpm knowledge:*`·`db:seed --knowledge-only` 스크립트는 `createAdminClient`(서비스 키, RLS 우회)를 쓰므로 영향이 없다(`scripts/knowledge/add.ts:43` 등).
  - 앱 안의 쓰기는 관리자 화면뿐이다(`lib/knowledge/save.ts`·`admin/library/actions.ts`).
  - 읽기 정책은 그대로 둔다.

### 3. [중간] 보낸·확인한 점검표를 성과관리팀이 지울 수 있다 — 확인

- 잠금 트리거 `inspections_guard`는 `before update`만 있다(`20260925090200_rls.sql:135`, 본문 `20261027100000_inspection_sent_guard.sql`). `inspections_staff`는 `for all`이다(`rls.sql:193`).
- 결과: 확인한 점검표를 「누구도 못 고침」이라고 하지만(CLAUDE.md 월간 점검 절), API 직접 호출로 **지우기**는 된다. 앱 코드에는 점검표를 지우는 곳이 없다(grep으로 확인).
- 고치는 방향: 보낸·확인한 행의 `delete`를 막는다. 트리거 `before delete`를 두거나, `inspections_staff`를 select·insert·update와 「draft일 때만 delete」로 나눈다.
- **주의**: 관리자 영구 삭제(`purgeCard`)는 `cards`를 지우고 `inspections.card_id … on delete cascade`(`20260925090000_core.sql:118`)로 점검표가 연쇄 삭제된다.
  - 연쇄 삭제 안에서 트리거의 `current_user`가 무엇으로 보이는지 확인해야 한다. PostgreSQL의 참조 무결성 동작은 참조 테이블 소유자 권한으로 돈다고 알고 있으나, 이 저장소에서 확인하지 않았다.
  - 확인 방법: PGlite 시험에서 보관 카드 영구 삭제가 계속 되는지 본다.

### 4. [낮음] 서버·DB가 화면보다 넓게 허용하는 곳 — 확인

모두 화면에는 단추가 없고, 서버 액션이나 API를 직접 부를 때만 해당한다. 의도라면 주석을 정리하고, 아니면 서버 검사를 더한다.

| 곳 | 화면 | 서버·DB | 근거 |
|---|---|---|---|
| 경평 검토 코멘트 달기 | 성과관리팀만(`canComment = staff && !deptView`) | 보고서를 읽을 수 있는 사람 누구나(같은 팀·주관 부서 담당자 포함). 함수 주석도 「보고서를 볼 수 있는 사람」 | `reports/[id]/page.tsx:76`, `reports/actions.ts:230-243`, `20260925091000_versions_reports.sql:174` |

### 6. [낮음] 오류 안내가 원인과 다르다 — 확인

- `deleteMaterial`: 잠긴(제출·승인) 보고서에서 지우면 RLS가 거절하는데, 안내는 「자기 부서 보고서만」이다(`reports/actions.ts:175-190`). 같은 파일의 `startMaterialUpload`·`setMaterialCards`는 `contentLocked`를 먼저 본다.

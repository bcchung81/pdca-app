# 사용자 입력부·입력 필수 점검(2026-10-27)

사용자 요청은 전체 화면에서 사용자 입력부만 골라 입력 필수 내용을 확인하는 것이다.

방법은 코드 정적 조사다.
- 화면 부품, 서버 액션, 마이그레이션(DB 제약·트리거·RLS)을 영역 셋으로 나눠 읽었다. 영역은 과제관리카드, 경평 초안, 점검·사용자·지식·관리·로그인이다.
- 무거운 주장은 메인 세션이 코드를 직접 열어 다시 확인했다(✓ 표시).
- 실제 화면 실행과 운영 DB 정책의 적용 상태는 확인하지 않았다. 운영 DB 보호로 e2e는 막혀 있다.

## 1. 역할별 「꼭 넣어야 하는 것」

### 부서 담당자

| 화면 | 필수 입력·조건 | 강제 |
|---|---|---|
| 내 과제(`/my`) 카드 편집 | 과제명은 비울 수 없다(저장 때 「과제명이 비었습니다」). 식별 칸(과제번호 등)과 확정된 고정 영역은 바꿀 수 없다 | 서버·DB |
| 「성과관리팀에 제출」 | 열린 작성본(이달에 고친 내용)이 있어야 한다 | 화면·서버 |
| 「한글 파일로 작성본 채우기」 | HWP·HWPX 1개, 30MB 이하, 자기 담당 과제 | 서버·버킷 |
| AI 작성지원 「실적 반영」 | 요청 칸에 실적 문장·수치를 넣거나 실적 자료를 첨부해야 한다 | 서버 |
| AI 「질문」·코멘트 「질문」 | 질문 글(질문 4,000자, 코멘트 2,000자까지) | 화면·서버 |
| 파일 첨부(AI 창) | PDF·HWP·HWPX·DOCX·XLSX·XLS·이미지, 파일당 50MB | 화면(서버는 크기만) |
| 경평 초안(`/my/report`) 「성과관리팀에 제출」 | 목차에 든 과제가 모두 과제별 초안을 가져야 한다(구성안만 있으면 없는 것으로 본다). 「자료 준비」 상태에서는 불가 | 화면·서버 |
| 경평 계량 실적 입력 | **필수 아님.** 비면 초안에 【확인】 자리표시로 남는다. 형식 검사 없음 | — |
| 받은 점검표 「확인」 | 보낸 상태의 자기 과제 점검표만 | 서버·RLS |
| 로그인 | 기관 메일 → 받은 메일 링크 → 화면 단추 | 화면·서버 |

## 2. 문제(심각도순)

### 높음

1. ✓ **경평 「승인 풀기」 단추는 늘 실패한다.**
   - 단추가 보내는 전이는 승인 → 제출(`components/reports/report-controls.tsx:170`)이다.
   - 전이 표(`lib/reports/model.ts:46`, DB `report_transition_ok`, `model.test.ts`)는 승인 → 작성 중만 허용한다.
   - 그래서 서버가 「이 단계로 바꿀 수 없습니다」를 돌려준다. 2026-10-10에 전이 표를 정비할 때 단추를 함께 고치지 않은 것으로 보인다.

### 중간

2. ✓ **보낸 점검표를 DB가 막지 않는다.**
   - 트리거 `guard_inspection_ack`는 확인한 점검표만 막는다(`20261010110000_report_inspection_guards.sql:46-63`).
   - 보낸 점검표의 잠금은 서버 액션 `inspectionWriteBlock`뿐이다. CLAUDE.md 서술(「보낸 점검표는 보내기 취소만」)보다 실제 보호가 약하다. 성과관리팀이 직접 호출하면 고칠 수 있다.
3. ✓ **사용자 수정은 서버가 「부서 담당자는 팀 필수」를 검사하지 않는다**(`app/(app)/users/actions.ts:59-80`).
   - 계정 만들기와 일괄 등록은 검사하지만 수정은 팀이 빈 부서 담당자도 저장한다. 그러면 담당 지정도 접근도 없는 계정이 된다.
   - 이름 필수 규칙도 경로마다 다르다. 만들기는 화면만, 수정은 없음, 일괄은 서버 검사다.
4. **화면에 글자 수 한도가 없고 서버가 조용히 자르는 곳이 많다.** 긴 글의 뒤가 말없이 사라진다.
   - ✓ 카드 돌려보내기 메모 1,000자
   - 삭제 까닭 300자
   - 현행화 건너뛰기 사유 300자
   - 카드 코멘트 2,000자
   - 보고서 코멘트 4,000자
   - 경평 글 직접 고침 600자(한 번에 60건)
   - 계량 실적 200자
   - 카드 밖 부분 칸 600·200·100자
   - 과제 대응 메모 1,000자
   - 사용자 이름 40자
5. ✓ **파일 형식 검사가 경로마다 다르다.**
   - 카드 전용 자료 올리기는 서버가 크기만 보고 형식은 보지 않는다(`app/(app)/cards/materials-actions.ts:65-72`).
   - 「카드 전용 자료」 창과 경평 근거 목록은 아무 파일이나 받는다. AI 창 첨부만 11종으로 거른다.
   - 받은 뒤 「AI가 못 읽음」이 된다.
6. **경평 계량 실적은 형식·지표 키 검사가 없다.** 「abc」도, 카드에 없는 지표 키도 저장된다. 동시 저장 충돌 방지도 없다.
7. **경평 직접 고침·구성안 글이 `cleanLine`을 거친다.** 사용자가 쓴 `<`·`>`(예: 「10% > 5%」)와 앞머리 `-`·`#`이 지워진다.
8. **업무 조건 일부는 서버 액션에만 있다.** 대상은 경평 제출 조건(목차 과제 모두 초안), 돌려보내기 메모, 점검표 보내기 조건이다. DB는 전이 표만 지킨다.

### 낮음

- 「실적 반영」은 빈 칸이어도 보낼 수 있다(서버가 안내). 「질문」은 화면이 막는다. 두 기능의 방식이 다르다.
- 「추가할 기간」(월별 실적 상자)은 형식·길이·중복 검사가 없다.
- 경평 제출 단추 툴팁이 과제 0개일 때 「…없는 과제가 있어: —」로 나온다. 아래 안내 문구는 맞다.
- 목차 쪽 배정 상한이 화면은 주요사업 3쪽, 서버는 10쪽이다.
- 보고서 코멘트는 화면에서 성과관리팀만 쓰지만, 서버·RLS는 같은 팀 부서도 허용한다.
- 점검표 저장(`saveInspection`)은 보관된 카드를 막지 않는다(AI 초안은 막는다).
- 점검표 화면은 공백만 있는 보완을 채운 것으로 보고 보내기 단추를 켠다. 그러면 서버가 거절한다.
- 일반 문서 제목은 화면 120자 제한만 있고 서버 제한은 없다.
- 업로드 크기는 클라이언트가 보낸 값으로 검사하고, 실제 한도는 버킷이 막는다.
- 쓰이지 않는 코드: `components/reports/block-editor.tsx`, `saveReportBlocks`. 지우자는 제안은 아니고 알려만 둔다.

## 3. 확인하지 못한 것

- `AckButton` 내부, 부서용 `/my/inspections`의 입력 전체, 점검표 편집기의 보기 모드.
- `private.can_write_unit_parts` 본문, `report_outline`의 쪽수·연도 DB check, `knowledge`·`card-originals` 버킷 정책.
- `finishMaterialUpload`가 저장소의 실제 객체 크기를 확인하는지.
- 운영 DB에 정책이 마이그레이션대로 적용돼 있는지. 마이그레이션 파일만 읽었다.

## 4. 반영(사용자 결정 — 네 가지 모두)

| 결정 | 반영 |
|---|---|
| 승인 풀기 버그 | 단추가 `UNAPPROVE_TO`(작성 중)로 보냄(`lib/reports/model.ts`, 시험이 전이 표 통과를 확인). 문구 「승인을 풀어 작성 중으로 되돌렸습니다 — 부서가 다시 고칠 수 있습니다.」 |
| 서버·DB 검사 보강 | 사용자 이름 판정 하나(`lib/users/name.ts` — 빈 이름·40자 초과 거절, 세 경로 공용), 수정 때도 부서 담당자는 팀 필수. 보낸 점검표는 DB 트리거도 내용 변경을 거절(마이그레이션 `20261027100000_inspection_sent_guard.sql`), 보내기 취소 서버 경로는 상태만 초안으로 |
| 글자 수 한도 표시 | 서버가 자르던 칸에 같은 상수로 화면 `maxLength`(`lib/cards/limits.ts`·`lib/reports/input-limits.ts`·`lib/inspections/model.ts INSPECTION_TEXT_MAX`·`lib/links/limits.ts`). contentEditable·목록 칸(경평 직접 고침 600자, 카드 밖 부분 줄 600자·40줄)은 저장 전에 막고 안내. 점검표 보내기 단추는 서버와 같은 정리(trim) 뒤 판정 |
| 파일 형식 검사 통일 | 카드 전용 자료 올리기 서버가 AI 창과 같은 11종만 받음(`materialNameProblem`), 「카드 전용 자료」 창·경평 근거 목록 올리기에 같은 `accept`·검사·안내(`FileDrop`의 `checkName`) |

- 운영 반영 순서: 새 트리거는 옛 서버 코드의 보내기 취소(내용까지 다시 씀)를 거절함 — **Vercel에 새 코드를 배포한 뒤 `pnpm db:push`**. 새 서버 코드는 옛 트리거에서도 동작.
- 승인 풀기 메모(사용자 결정): 승인을 풀 때도 돌려보내기처럼 「부서가 고칠 점」 메모가 필수이고 그 메모가 review_note를 덮어씀(`lib/reports/model.ts needsReturnMemo`, 확인 창은 돌려보내기 부품 재사용). DB `guard_report`는 성과관리팀의 검토 메모 쓰기와 승인 → 작성 중 전이를 허용함(확인).

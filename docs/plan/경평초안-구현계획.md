## 2단계 — 구성안 승인 단계(재료표 → 구성안 → 사람 승인 → 집필)

목표: 한 번의 AI 호출이 자료 해석·구성·집필을 한꺼번에 하던 것을 나눠, 사람이 구성안을 보고 고른 뒤 집필함. 짜임이 실행마다 흔들리는 문제와 「왜 이 틀인가」가 없던 문제를 풂(2026-09-27 승인된 로드맵 P2).

- 2-1 구성안 AI 호출(구조화 출력): 재료표(사실·수치·시점·출처 구절, 없는 자료는 「담당자 확인 필요」) + 구성안(핵심 메시지 한 문장 · 평가 논점 2~3 · 이야기 틀과 고른 이유·차선안 · 블록 순서(라벨·종류·담을 재료 번호) · 그림 자리 · 쪽 배치 어림). 코드 검증: 재료 출처 원문 대조, 없는 재료를 쓴 블록 표시, 판면 어림
- 2-2 집필 호출: 승인된 구성안을 입력으로 받아 블록을 채움(짜임은 바꾸지 않음) → 지금의 검증·고치기
- 2-3 화면: 과제별 초안 화면에 「구성안 만들기 → 보기·고치기(블록 순서·틀·그림 자리) → 승인하고 집필」. 지금의 「AI로 바로 만들기」는 남김
- 2-4 저장: 구성안과 승인 상태를 저장(DB 변경 — 마이그레이션·RLS·역할별 테스트)
- 결정: 저장 방식(초안 테이블에 칸 추가 / 새 테이블), 구성안에서 사람이 고칠 수 있는 범위, 바로 만들기를 남길지
- 검증: 구성안 → 집필 초안이 구성안 짜임을 지키는지(블록 순서 일치율), 평가 세트에서 짜임 흔들림(같은 카드 두 번 실행 시 서명 일치) 감소

규모: 대(AI 2단계·화면·DB).

**결과(2026-09-27)**: 사용자 결정 — 초안 테이블에 칸 추가 · 고칠 범위 순서·빼기·틀·그림 · 바로 만들기 남김 · 재료표 화면에 보임. 만든 것: `lib/reports/composition.ts`(정리·원문 대조·판면 어림·`fitComposition`·블록별 높이 예산·**글 한도** `blockLimits`·`planLimitIssues`·편집 적용·집필 요청·짜임 준수), `resources/prompts/report-outline/`, `callReportOutline`, 마이그레이션(운영 DB 적용), 서버 액션(`runReportOutline`·`saveReportOutline`·`approveReportOutline`), 화면(구성안 패널·「구성안 만들기」). 평가: J(구성안만) 첫 초안 128%·최종 95%(84~108) → K(글 한도 추가) 첫 초안 112%·최종 98%(91~106)·짜임 그대로 8/8·교정 2회 2장·1건 121초(구성안 55 + 집필 67). 남은 것: 0.5쪽 넘침 2장(104~106%), 첫 초안 110% 이하는 조금 못 미침, 화면의 구성안 패널은 운영 DB에 구성안을 만들지 않아 실제 구성안이 든 모양은 눈으로 확인 못 함(평가 폴더 `.outline.json`으로 확인).

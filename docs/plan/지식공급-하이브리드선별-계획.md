# 지식 공급 하이브리드 선별 — 외부 컨설팅 반영 계획 (2026-10-26, 결정 반영 — 착수 전)

- 근거: 외부 컨설팅 의견(2026-10-26 수신, 「하이브리드 RAG + 판단 모델 선별」·「공통 규칙 문서」·「단계적 병행 비교」) + 이 저장소 코드 대조 + 운영 DB 읽기(2026-10-26, `card_knowledge_scope`·`knowledge_chunks` select만).
- 상태: §7 결정은 2026-10-26 확정(추천안대로 + Claude는 CLI로만). 0~7단계 구현·병행 비교 완료(2026-10-26) — 결과 `docs/plan/지식공급-하이브리드선별-결과.md`(미리 정한 규칙을 통과한 기능 없음, 기본은 통째로 넣기 유지). 8단계(운영 기본값)는 결과 문서 §9 결정 뒤.
- 관련: 지금 방식 `docs/design/knowledge.md`(「규칙 범위 전부」·대응표는 거르지 않음), 요구사항 R1 `docs/reference-materials.md` §1, 앞선 선별·Jev 실험 `docs/plan/참고자료-진행현황.md`(「Jev 실험」·「3-5 재정의 진행 기록」).
- 표기: 「확인」은 코드·DB로 확인한 값, 「추정」은 확인하지 않은 판단입니다.

## 1. 결론

1. 컨설팅의 큰 방향(지금은 통째로 넣기가 맞는 출발점, 넓히기 전에 선별 방식을 병행 비교)은 2026-10-22 내부 재검토 결론과 같습니다. 제안 여섯 가지(태그·하이브리드 검색·판단 모델·확인 누적·규칙 문서·병행 비교)를 모두 단계에 넣습니다.
2. **정답지가 이미 있습니다.** 2026-10-12에 CLI로 판정한 대응표 확정·제외 417건(카드 95장)으로 「확정 대응표를 정답지로 과제 5~10개 시험」을 바로 할 수 있습니다. 다만 지적 계열에만 있어 실사 질의응답·전년 절은 판정을 더해야 합니다.
3. 부서는 오픈 전이라 사용빈도 실측이 없습니다. **비용은 시나리오 시뮬레이션으로 기본값을 정하고, 오픈 뒤 `ai_requests` 실측으로 다시 계산**합니다.
4. 통째로 넣기 경로는 그대로 두고, 선별 방식은 **기능별로 켜는 별도 경로**로 더합니다. 운영 적용은 병행 비교(§6 판정 규칙)를 통과한 기능만 합니다.
5. R1은 「끝까지 읽힌 근거 메모」를 허용하므로 규칙 문서는 R1 안에 들어갑니다. 사례류 선별은 「판정기가 범위 전부를 읽음(R1 유지)」과 「상위 후보만 판정(R1 완화)」 두 갈래를 시험에서 같이 잽니다(§4.2).

## 4. 목표 구조

### 4.1 선별 방식의 요청 구성(통째로 넣기 경로는 바이트까지 그대로)

| 순서 | 내용 | 캐시 |
|---|---|---|
| 1 | 시스템(지금과 같음) | 기능별 공유 |
| 2 | 공통 규칙 문서(트랙 + 이 사업·지표 절) — 기준류 원문 자리를 대신함, 「근거 아님」 표지 | 사업·지표별 공유 |
| 3 | 고른 조각 원문(확정 + 판정 통과, 자르지 않음) | 카드별 |
| 4 | 범위 전체 조각 제목 목록표(있는 것을 알림) | 카드별 |
| 5 | 카드·카드 전용 자료(지금과 같음 — 선별 대상 아님, 금기 4와 무관) | 카드별 |

- 인용·숫자 대조는 지금처럼 **원문 조각**으로 합니다. 규칙 문서는 숫자·인용 근거에 쓰지 않습니다(작성 방법론과 같은 취급).
- 규칙 문서 조각은 통째로 넣기 경로의 층(`layerOf`)에 들어가지 않게 범위 밖으로 둡니다.
- 적용 후보 기능: 작성지원 요청 종류 넷·질문·코멘트·경평 구성안·집필. **월간 점검은 제외**(자료 범위가 이미 고정 발췌).
- 평가 관점(`lib/reports/lens.ts`)의 검색 순서(`searched`)를 하이브리드 순위로 바꿉니다(컨설팅이 짚은 「단어 겹침 위주」).

### 4.2 R1과의 관계

R1: 「해당 참고자료를 빠짐없이·잘림 없이 본다. 한 번에 안 들어가면 자르지 않고 끝까지 읽힌 근거 메모로 넣거나 멈추고 알린다」.

| 갈래 | 기준류 | 사례류(지적·실사·전년 절·사례) | R1 |
|---|---|---|---|
| 유지형 | 규칙 문서(전부 읽고 만든 근거 메모, 빠짐 0 검산) | 판정기가 범위 안 조각을 **전부** 읽고 판정, 검색은 순서·우선순위만 | 문구 그대로 지킴. 오프라인 판정 비용·시간이 큼 |
| 완화형(컨설팅안 그대로) | 같음 | 하이브리드 상위 50~100개만 판정, 나머지는 제목 목록으로만 | 후보 밖은 아무 모델도 안 읽음 → R1 완화 |

시험 카드는 정답을 매기려고 어차피 범위 대부분을 판정하므로(§5 2단계) 두 갈래를 같은 정답으로 비교할 수 있습니다.

### 4.3 판정기 편향 보정

판정기끼리 갈린 것만 사람이 판정합니다(표본 또는 전부 — §7 D4). 이 판정은 정답 보정과 `/links` 확인 누적(제안 ④)을 겸합니다.

### 1. 조각 성격 함수
- `lib/knowledge/chunk-role.ts`: `chunkRole(chunk)` → 실적 근거·조항 기준·평가위원 지적·실사 질문·전년 보고서·방법론 사례, `isLatest(chunk)`(`revision-note.ts`의 최신본 규칙 재사용). 시험은 파서가 내는 `unit_type` 전부를 열거해 미분류 0을 확인.

### 2. 정답지 넓히기
- 시험 카드 6~9장: 지적 계열 정답이 확정·제외 둘 다 있는 카드에서 두 트랙 반반.

- 대기 candidate 556건 판정은 대응표 품질을 올리는 별도 일로 같은 단계에서 처리합니다.
- 판정 묶음 만들기·결과 반영 스크립트(`scripts/eval/label-scope.ts`, `--dry-run` 기본). 운영 DB(`card_knowledge_scope`)에 쓰는 것은 **실행 때 건수를 보고하고 승인 뒤**(기존 규칙). `method`는 바꾸지 않고 `meta.labeler`(판정 날짜·경로)를 남깁니다.

### 3. 하이브리드 검색
- `lib/knowledge/hybrid.ts`(순수: 성격·범위 필터, 순위 융합 RRF) + 시험, `scripts/eval/hybrid-recall.ts`(로컬 임베딩 계산 → PGroonga `search_knowledge` 읽기 → 융합 → 재현율 표).
- 임베딩은 시험 단계에서 스크립트 메모리로 계산하고 표를 만들지 않습니다. 채택되면 pgvector 열이 있는 표(RLS + `lib/db/migrations.test.ts` 사례)로 옮깁니다.
- 요청 때 검색하지 않습니다. 카드별 결과를 처리기(`prep_jobs`)가 미리 계산해 대응표에 점수·순위로 넣습니다(앱 실행 중 임베딩·로컬 경로 의존 없음 — 금기 1).
- 시험할 임베딩 모델 후보는 로컬 다국어 모델 2개 안팎(개발 의존성 추가 — §7 D1).

### 4. 판정기 비교
- 기존 `lib/ai/typesafe.ts`·`scripts/eval/jev-match-batch.ts`·`lib/ai/match.ts`를 정답 대조만 더해 재사용(`scripts/eval/judge-compare.ts`).

### 5. 공통 규칙 문서
- 대상: 기준류(관리계획 해당 부분·편람·Pool·AX·목표지표·핵심공통항목). 트랙 공통 절 + 사업·지표별 절.
- 프롬프트 `resources/prompts/rules-digest/`, 검산 순수 함수 `lib/knowledge/rules-digest.ts`: ① 인용한 조각 키가 실재 ② 따옴표 문구가 원문에 글자 그대로(기존 인용 대조 재사용) ③ 기준류 조각마다 규칙 하나 이상이 가리키거나 「해당 없음」 부록에 있음(빠짐 0).
- 생성·검산·저장 스크립트 `scripts/knowledge/rules-digest.ts`(`--dry-run` 기본). 검수가 끝난 판만 DB 문서로 저장(기관 자료라 저장소 밖, `meta.usage = rules_digest`, 원문 조각 해시 기록). 원문이 바뀌면 해시가 바뀐 조각을 가리키는 절만 다시 만듭니다.

### 6. 선별 방식 조립
- `lib/knowledge/select.ts`(순수 `buildSelectedBundle`) — `buildBundle`은 손대지 않음. `lib/ai/context.ts` `loadCardBundle`이 설정에 따라 고름.
- 켜는 설정: 환경변수 하나(예: `KNOWLEDGE_SELECT_FEATURES=writer,chat`, 비면 모두 통째로 넣기) → `.env.example`에 추가(`lib/ops/env-keys.test.ts`).
- 시험: 통째로 넣기 출력 바이트 불변, 선별 방식에서 확정 전부 포함·제외 전부 빠짐·카드 전용 자료 불변·규칙 문서가 층에 안 섞임.
- 문서: `docs/design/knowledge.md`에 선별 방식 절 추가. CLAUDE.md는 40KB 한도 근처라 「대응표는 거르지 않음」 줄만 바꿔 씀.

### 7. 병행 비교
- 시험 카드 6~9장 × 작성지원 개선 제안·질문·경평 구성안+집필(§7 D5 범위) × 방식마다 2회(같은 카드 재실행 인용 겹침이 48~68%였으므로 잡음 폭부터 확인).
- 기존 도구: `scripts/eval/judge-run.ts`(블라인드 심사)·`eval-report-score.ts`(결정론 점수)·`context-size.ts`(입력 크기). 같은 사업 안 초안끼리 틀·라벨 겹침도 참고로 셉니다(2026-10-22 동질성 집계와 같은 방식).
- 2026-10-07 선별 시험과 다른 점을 결과에 명시: 규칙 문서·하이브리드 후보·확정 정답·제목 목록표.

### 8. 오픈 기본값
- 7단계 결과 + 0단계 시뮬레이션으로 기능별 기본 방식을 정해 켜는 설정에 반영. 오픈 뒤 `ai_requests`로 캐시 적중·요청 수를 실측해 시뮬레이션을 다시 돌립니다.

## 6. 미리 고정하는 판정 규칙

실행 전에 고정하고, 결과를 본 뒤 바꾸지 않습니다.

### 6.1 검색(3단계)
- 정답(확정) 재현율: 후보 100개에서 **≥95%**, 지적 계열·실사·전년 절을 따로 보고. 같은 정답으로 기존 글자 TF-IDF·PGroonga 단독을 기준선으로 다시 잼.
- 풀 밖 표본에서 확정이 나오면 그 비율을 「검색이 못 보는 몫」으로 따로 적음.

### 6.2 판정기(4단계)
- 확정 정답을 제외한 비율 **≤2%**, 애매(사람 확인) 몫 **≤30%**. 둘 다 통과한 판정기 중 싼 것을 고름. 없으면 판정기 선별은 접고 유지형 갈래에서는 경량 모델 전부 판정을 씀.

### 6.3 병행 비교(7단계) — 기능별로 판정
- 블라인드 심사: 선별 방식 승 + 비슷 ≥ 통째로 넣기 승
- 「카드에 있는 것을 없다고 함」 0건, 근거 없는 숫자 증가 0건
- 요청 입력 −60% 이상
- 넷 다 통과한 기능만 운영 적용 후보

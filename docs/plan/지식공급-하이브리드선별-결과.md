# 지식 공급 하이브리드 선별 — 구현·비교 결과 (2026-10-26)

- 계획: `docs/plan/지식공급-하이브리드선별-계획.md`(외부 컨설팅 반영, 결정 D1~D6). 이 문서는 그 0~7단계를 구현하고 같은 카드로 「통째로 넣기(기존)」와 「선별(새)」을 돌려 비교한 결과입니다.
- 조건: Claude는 모두 로컬 **CLI**(sonnet-5-5 생성, opus-5-5 판정·심사), Jev는 TypeSafe API, 운영 DB는 읽기만(쓰기 0). 실험 산출물(판정·선별·규칙 문서·초안)은 git 밖 `docs/analysis/eval/2026-10-26-select/`.
- 규모(사용자 결정): 카드 6장(주요사업1/7-가·2/1-가·3/5-가, 경영관리1/1-1·3/3-1·4/4-2) × 작성지원·질문·경평 구성안+집필 × 방식 2 × **1회**. 심사자 Claude CLI만. 1회라 같은 설정의 변동 폭은 재지 못했고, 2026-10-07 측정(같은 카드 재실행 인용 겹침 48~68%)을 참고 잡음으로 봅니다.
- 표기: 「실측」은 이번 실행 값, 「추정」은 시나리오 계산입니다.

## 1. 결론

1. **미리 정한 판정 규칙(계획 §6.3)을 네 가지 모두 통과한 기능은 없습니다.** 규칙대로면 운영 적용 후보가 없고, 기본값(통째로 넣기, `KNOWLEDGE_SELECT` 비움)을 유지합니다.
2. **트랙별로 갈립니다.** 주요사업은 품질이 같거나 나으면서(경평 3장 모두 선별 우세, 7.53 대 6.37) 요청당 비용이 40% 안팎 줄었습니다. 경영관리는 경평 품질이 떨어졌고(3장 모두 통째로 넣기 우세, 7.07 대 6.10) 비용은 20% 안팎만 줄었습니다.
3. **대화형(작성지원·질문) 연간 비용은 약 −34%(추정)** 입니다. 과제당 월 5회, 캐시 식은 요청 80% 시나리오에서 약 $4.3k → $2.9k(연 약 $1.5k 절감)입니다. 다만 같은 사업 카드가 5분 안에 이어 들어오는 경우(캐시가 따뜻한 일괄 작업)는 선별이 오히려 비쌉니다.
4. **컨설팅이 제안한 구성요소 가운데 효과가 확인된 것은 「사례류 선별」 하나입니다.** 임베딩 하이브리드 검색은 앱이 이미 쓰는 글자 TF-IDF보다 나아지지 않았습니다. Jev는 재현율을 높이려면 애매 몫이 70%를 넘었습니다. 규칙 문서는 검산은 통과했지만 줄어드는 폭이 작았습니다(주요사업 41~53%, 경영관리 약 100%).

## 3. 선별 재료

### 3.1 정답지(실측)

- 시험 카드 6장의 범위 안 사례류 조각 **999건 전부**를 CLI opus(high)로 판정했습니다. 결과는 yes 225 · maybe 74 · no 700이고, 9분이 걸렸습니다.
- 기존 CLI 판정(2026-10-12)과 겹치는 58건 중 maybe를 뺀 55건의 일치율은 78%입니다. 기존 확정을 이번에 no로 놓친 것은 0건입니다.
- 갈린 30건 심판: 사용자 8건(모두 yes)과 opus xhigh 22건입니다. 판정기별 일치율은 정답지 80%, Jev p≥0.2 60%, 경량(현행 매칭) 37%입니다. 정답지 yes를 심판이 뒤집은 것은 0건입니다.
  - 한계: 사용자가 부서 내용을 몰라 22건을 opus로 대신했습니다. 그래서 **Claude 편향 보정은 하지 못했습니다.**

### 3.2 검색(재현율, yes 225건 기준, 실측)

| 방식 | @50 | @100 |
|---|---|---|
| 글자 TF-IDF(앱이 「닮은 순」에 쓰는 함수) | **85%** | **97%** |
| PGroonga | 61% | 88% |
| 로컬 임베딩 bge-m3 | 79% | 95% |
| 융합(bge-m3 + PGroonga + TF-IDF) | 80% | 97% |
| 현행 대응표(auto·confirmed, 카드당 평균 26건) | — | 66% |

→ 임베딩·pgvector를 더해도 이 규모(카드당 후보 110~236건)에서는 얻는 것이 없었습니다. 현행 대응표는 관련 조각의 ⅓을 놓칩니다.

### 3.3 판정기(실측, §6.2 기준 — 놓친 yes ≤ 2%, 애매 몫 ≤ 30%)

| 설정 | 고른 글자(전체 99만 자 중) | yes 재현율 | 놓친 yes | 애매 몫 |
|---|---|---|---|---|
| Jev p≥0.2 (**선택**) | 30.8만(31%) | 95.6% | 4.4% | 70.9% |
| Jev p≥0.5 | 16.4만 | 68.9% | 31.1% | 47.9% |
| 경량 auto+candidate | 23.3만 | 89.8% | 10.2% | 16.0% |
| TF-IDF·융합 상위 100(문턱만) | 77.2만 | 96.9% | 3.1% | — |

- 통과한 설정은 없습니다. 규칙대로 놓친 yes가 가장 적은 판정기 설정(Jev p≥0.2)을 골랐습니다.
- 완화형(상위 100 안에서만 판정)은 크기가 같으면서(30.6만 자) 놓친 yes가 7.6%였습니다. 그래서 생성 비교는 유지형으로 돌렸습니다.
- Jev 비용: 요청 44회, 입력 91만 토큰, 13초입니다.

## 4. 입력 크기(결정론 실측, 글자)

| 요청 | 주요사업 통째로 → 선별 | 경영관리 통째로 → 선별 |
|---|---|---|
| 작성지원·질문 | 27.0만~31.0만 → 9.3만~12.8만 (**−59~66%**) | 16.7만~24.3만 → 9.1만~18.0만 (−26~45%) |
| 경평 집필(1차) | 33.4만~37.7만 → 16.7만~20.9만 (−45~50%) | 18.8만~27.5만 → 11.6만~21.7만 (−21~38%) |

선별 요청의 구성은 다음과 같습니다.
- 시스템
- 규칙 문서와 그대로 두는 조각(사업별로 같아 캐시 공유)
- 고른 조각 원문(카드별)
- 고르지 않은 조각 제목 목록과 요청 글

경영관리가 덜 주는 이유는 두 가지입니다.
- 고른 조각이 많습니다(카드당 37~75건 — 실사 답변 비중이 큼).
- 규칙 문서가 줄지 않았습니다.

## 5. 품질(블라인드 심사, Claude CLI opus — 1회)

| 기능 | 결과(통째로 승 · 선별 승 · 비슷) | 축 평균(통째로 / 선별) | 심사자가 센 오류(통째로 / 선별) |
|---|---|---|---|
| 작성지원 6쌍 | 2 · 3 · 1 | 근거 4.17 / 4.17, 유용 4.33 / 4.33 | 카드에 있는데 없다고 함 1 / 1, 지어낸 숫자 0 / **1**, 덮어쓰기 2 / 1, 사실 오류 1 / 0 |
| 질문 6쌍 | 1 · 3 · 2 | 근거 3.83 / **4.33** | 카드에 있는데 없다고 함 0 / **1**, 지어낸 숫자 1 / 0, 사실 오류 2 / 0 |
| 경평 주요사업 3장 | 0 · **3** · 0 | 종합 6.37 / **7.53** | 지어냄 5 / 1 |
| 경평 경영관리 3장 | **3** · 0 · 0 | 종합 **7.07** / 6.10 | 지어냄 4 / **11** |

- 코드 검사의 「근거에 없는 숫자」는 경평 12건 모두 0입니다. 심사자가 센 「지어냄」은 의미상 근거 부족으로, 이와 다른 기준입니다.
- 결정론 점수표(경평)에서는 두 방식이 대체로 비슷합니다. 다른 점은 다음과 같습니다.
  - 주요사업 선별 초안의 경고가 더 많습니다(2→6, 4→7).
  - 경영관리1/1-1 선별 초안이 깁니다(판면 833 대 685mm, 문장 125 대 87).
  - 평가 논점 충족은 카드마다 엇갈립니다.
- 작성지원·질문은 트랙별 경향이 뚜렷하지 않고, 심사 확신도 대부분 낮음~중간입니다.

한계:
- 1회 실행입니다.
- 심사자는 Claude 하나입니다.
- 작성지원 쌍 6개 중 5개에서 선별 답이 A 자리에 놓였습니다(순서 편향 가능).
- 선별 답 7건에 방식을 드러내는 문구(「자료 확인 필요」 등)가 있어 블라인드가 완전하지 않습니다.

| 상태 | 주요사업 작성지원 | 주요사업 질문 | 경영관리 작성지원 | 경영관리 질문 |

## 9. 다음 선택지(결정 필요)

1. **주요사업만 반복 확인**: 같은 6장(또는 주요사업 6장)을 2회 더 돌려 잡음 폭을 잰 뒤 주요사업 대화형·경평 적용을 판단합니다.

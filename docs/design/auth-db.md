## 데이터베이스(Supabase)

- 스키마는 `supabase/migrations/`에만 씁니다. 대시보드에서 직접 바꾸지 않습니다.
- 모든 테이블에 RLS를 켭니다. 권한 판정은 `private` 스키마 함수(`can_read_card` 등)로 합니다. 새 테이블·정책을 만들면 `lib/db/migrations.test.ts`에 역할별 사례를 더합니다.
- 저장소 키에는 한글을 쓰지 않습니다(카드는 `uid`).
- 비밀 키(`SUPABASE_SECRET_KEY`)는 서버·스크립트에서만 씁니다. `NEXT_PUBLIC_*`로 내보내지 않습니다. 서비스 키 클라이언트(`lib/supabase/admin.ts`)는 Auth 관리 API가 필요할 때만, 관리자 확인(`requireRole`) 뒤에 씁니다. 데이터 수정은 로그인 사용자 권한으로 해서 RLS가 판정하게 합니다. 예외(주석에 목록): 처리기(`lib/prep/store.ts`), 계정 만들기·로그인 차단 실패 기록(`access_events` `user_added`·`ban_failed`), **첨부 읽은 글**(`card_materials`·`report_materials`의 `parsed_text` 등 — 2026-11-17 `20261117100000`: 로그인 사용자는 그 칸을 넣지도 고치지도 못하고 서버가 저장소에서 읽은 결과만 `saveParsed`가 씀. 사용자 권한으로 그 행을 읽을 수 있고 경로가 같을 때만, 상세 `docs/design/ai-assist.md`). 운영 반영 순서는 새 코드 배포 먼저 → 바로 `db:push`(거꾸로면 그 사이 옛 코드의 읽은 글 저장이 거절돼 첨부가 「아직 안 읽음」으로 남음).
- 업무 규칙은 서버 액션과 DB 트리거 둘 다에 둡니다(API로 바로 쓰거나 읽고-쓰기 사이에 끼어들어도): 보고서 전이 표·확인한 점검표 잠금(`20261010110000`), 작성본 식별 칸(새 작성본의 id·group·taskNo = 원장, 고칠 때 과제·식별 칸 불변 — 성과관리팀도)·마지막 활성 관리자(`20261010120000`). **부서 직접 확정(`20261027110000`, 2026-10-27)**: 부서 담당자도 자기 담당 활성 카드(`can_write_card`)의 원장을 고치되 트리거 `guard_card`가 내용(`data`·`title`·`data_rev`+1·`updated_by` 본인·`original_html` 비움)만 허용하고 그 밖의 열·식별 칸·잠긴 고정 영역은 거절(정책 `cards_dept_update`), 작성본 트리거 `guard_card_version`은 부서의 작성 중 → 확정(확정자 본인)을 허용, 이력 `card_edits`는 부서 insert 정책(`card_edits_dept_insert`), 보고서 전이 표 `report_transition_ok`에 작성 중 → 승인(부서 확정)·승인 → 작성 중(확정 취소)을 더하고 `guard_report`가 승인자·승인 시각을 지킴(확정한 보고서의 내용은 확정 취소 뒤 고침). 보낸 점검표 잠금 `20261027100000`은 성과관리팀의 내용 변경도 거절. 이 둘은 운영 반영 순서가 있음(`docs/ops/운영-전환.md` 「부서 확정 반영」). 트리거 메시지와 서버 문구를 맞춥니다. **웹 취약점 점검(`20261116100000`·`20261116110000`, 2026-11-16)**: 현행화 묶음·항목 위조 트리거 `guard_card_import`·`guard_card_import_item`, AI 호출 기록은 표 직접 쓰기를 거두고 rpc `start_ai_request`·`finish_ai_request`로만(상세 `docs/design/ai-assist.md`, 앞 것은 순서 무관 · 뒤 것은 새 코드가 의존하므로 코드보다 먼저 `db:push`). 이 둘과 `20261010100000`(AI 호출 진행 중 기록)은 운영 반영 2026-10-10 — 새 코드가 의존하므로 새 DB에도 코드보다 먼저 `pnpm db:push`. 지표 단위 부분 표 `eval_unit_report_parts`(`20261016100000` — 경영관리 R5b 뒷단, 권한·가드는 `docs/design/report-draft.md` 「R5b 뒷단」)는 운영 반영 2026-10-16(사용자 승인) — 화면 `/reports/business/<지표>/parts`가 의존.
- **앱 서버 경유 표지(근본책 1~3단계, 2026-11-17 — `20261117120000`·`20261117130000`·`20261117140000`·`20261117150000`)**
  - **왜**: 로그인 사용자는 공개 키와 자기 토큰으로 DB(PostgREST)에 바로 쓸 수 있습니다. RLS는 「어느 행」만 보고 「어떤 값」은 보지 않으므로, 서버 액션의 검증·다시 점검(zod·`cleanLine`·`recheckSection` 등)을 건너뛴 값이 저장될 수 있었습니다(초안의 없는 숫자·경고·판면 값 등). 서비스 키로 쓰기·표마다 rpc·값 검증 트리거 대신 이 방식을 고른 이유: 역할·RLS 행 판정·가드 트리거·`auth.uid()`·감사 기록을 그대로 두고, 서비스 키 예외를 늘리지 않으며, 판정값 검증(TS 코드)을 DB로 옮기지 않아도 됩니다.
  - **무엇을**: 서버가 만드는 사용자 권한 클라이언트(`lib/supabase/server.ts`·`job-client.ts`)만 서버 전용 비밀 `APP_WRITE_KEY`를 머리글 `x-app-write`로 싣습니다(`lib/supabase/app-write.ts`, 브라우저 클라이언트는 안 실음). DB는 `private.app_write()`가 그 값의 sha256을 `private.app_write_key`(해시만, 누구에게도 권한 없음)와 대조합니다. 머리글 이름은 PostgREST가 `request.headers`에 소문자로 담는 것을 전제로 합니다. 머리글이 없거나 빈 값·다른 값이면 false.
  - **어디까지**: 공개 스키마에서 로그인 사용자가 쓸 수 있는 **모든 표**의 삽입·갱신·삭제 정책과 로그인 사용자가 부를 수 있는 **모든 security definer rpc**.
    - 1단계 B(`20261117130000`): 경평 초안 표 `card_report_drafts`·`report_draft_edits`·`eval_unit_report_parts`.
    - 2·3단계 표(`20261117140000`): 부서도 쓰는 `cards`·`card_versions`·`reports`·`card_edits`·`card_imports`·`card_import_items`·`card_materials`·`report_materials`·`report_comments`·`report_material_cards`·`ai_results`·`prep_jobs`·`profiles`와 성과관리팀·관리자만 쓰는 `inspections`·`card_assignees`·`card_knowledge_scope`·`eval_units`·`knowledge_documents`·`knowledge_chunks`·`report_outline`·`task_map`. 쓰기 권한이 없는 `teams`·`knowledge_card_links`·`card_knowledge_select`의 FOR ALL 정책은 읽기 정책으로만 남깁니다.
    - 2단계 rpc(`20261117150000`): 로그인 사용자가 부를 수 있는 공개 security definer 함수 7개 — 쓰기 2개(`start_ai_request`·`finish_ai_request`)와 읽기 5개(`report_submit_cards`·`mg_biz_refs`·`mg_biz_ref_texts`·`mg_biz_stale`·`report_outline_context`) — 는 첫 `begin` 바로 뒤에서 표지가 없으면 권한 오류(42501, 「앱 서버를 거친 요청만 받습니다」)로 거절하고 나머지 본문은 예전 정의 그대로입니다. sql 함수 5개는 이 첫 줄을 넣으려고 plpgsql(`return query` + 원래 select)로 바꿨고 인자·반환·변동성·search_path·권한·설명은 같습니다. 확인용 `app_write_probe`만 예외.
    - 저장소(`20261118100000`): `storage.objects` 쓰기 정책 9개(넣기 4·지우기 3·FOR ALL 2). FOR ALL은 이름을 지키고 USING·WITH CHECK 둘 다 표지 — 같은 사람의 읽기는 `…_read` 정책이 맡아 줄지 않음. Storage 서버가 요청 머리글 전체를 `request.headers`로 넘기므로(supabase/storage `scope.ts`) 표와 같은 판정. 서명 업로드 주소는 서버 액션이 만들 때 넣기 정책을 사용자 권한 + 표지로 시험하고, 브라우저의 그 주소 올리기는 Storage가 서비스 역할로 씀(표지 무관). 지우기는 권한 없는 이름을 오류 없이 건너뛰므로 서버는 지운 수를 봄(`lib/storage/remove.ts`, 로그 `storage_remove_failed`). 행 없는 파일 정리는 `pnpm storage:prune-orphans`.
    - 경평 초안 판 기록(`20261118120000`): `card_report_draft_versions`는 사용자 쓰기 정책·권한이 없고(authenticated select만) 트리거(`private.keep_card_report_draft_version`, security definer)만 씁니다. 표지 확인은 초안 표 쓰기 정책이 맡습니다. 요청별 머리글 `x-draft-save`는 표지 머리글과 같은 길(PostgREST `request.headers`)로 읽으며, 위조해도 판이 덜 쌓일 뿐입니다.
    - **읽기 rpc도 표지를 요구하는 이유**: definer 함수는 소유자 권한으로 돌아 RLS보다 넓게 읽고(다른 팀 초안 발췌·확정 조건 재료 등), 누가 무엇을 보는지는 함수 본문의 판정만이 정합니다. 이 함수들은 앱 화면·서버 액션이 정해진 인자로만 부르므로, 표지로 앱 밖 호출을 막아 판정 본문을 공격면에서 뺍니다. 표지는 판정을 좁히기만 하고 넓히지 않습니다. 부르는 곳은 모두 사용자 권한 서버 클라이언트(`createClient`·`createJobClient`)이고 서비스 키로 부르는 곳은 없습니다 — 앞으로 스크립트에서 부르려면 그 클라이언트도 `appWriteHeaders()`를 실어야 합니다.
    - 모양: 행 판정(누가 어느 행)은 바꾸지 않고 `and private.app_write()`만 더합니다 — 삽입·갱신은 WITH CHECK(갱신 USING은 예전 그대로라 표지 없는 갱신은 0행이 아니라 RLS 오류), 삭제는 USING(0행). **FOR ALL 정책은 두지 않습니다**: ALL의 USING은 읽기에도 쓰여 표지를 넣으면 읽기까지 막히고 안 넣으면 삭제가 표지 없이 통과하므로, 명령별로 나누고 읽기 정책은 예전과 같은 식으로 남깁니다. 읽기는 표지와 무관합니다.
    - 정책을 거치지 않는 경로: 가드·감사 트리거와 security definer 트리거 함수(예: `prune_ai_results`), on delete cascade는 표지와 무관하게 예전처럼 돕니다(그 앞의 쓰기가 이미 정책을 통과). service_role·postgres(스크립트·처리기)는 RLS 밖이라 영향 없음.
  - **구조 시험**(`lib/db/grants.test.ts` 「쓰기 정책 구조」): 마이그레이션 전부를 올린 뒤 ① 로그인 사용자·비로그인·PUBLIC에 걸린 공개 표의 허용 정책 가운데 FOR ALL이 하나도 없고 ② 삽입·갱신은 WITH CHECK, 삭제는 USING의 **맨 위 AND 항 하나가 정확히 `private.app_write()`** 이며(OR·NOT·CASE 안이나 글자 속에 있으면 인정 안 함) ③ 로그인 사용자·비로그인이 실행할 수 있는 공개 security definer 함수는 plpgsql 본문 첫 문장이 `if not private.app_write() then raise exception …; end if;`인지 봅니다. 실패 메시지에 표지 빠진 정책·함수 이름이 나옵니다. 예외는 이름과 이유를 적은 목록(`POLICY_EXCEPTIONS` — 비어 있음, `DEFINER_EXCEPTIONS` — `app_write_probe`)에만 두고, 없는 이름이 남으면 실패합니다. 저장소는 `grants.test.ts` 「저장소 객체의 쓰기 정책」(정책 14개 목록 고정)과 `migrations.test.ts` 「앱 서버 경유 표지 — 저장소 객체」. 역할별 허용·거절 사례는 `lib/db/migrations.test.ts`(표)·`lib/db/app-write-rpc.test.ts`(rpc 7개: 표지 없음·빈 값·틀린 값 42501, 맞으면 예전대로, 로그인 없음이어도 표지 거절이 먼저).
  - **새 표·rpc를 만들 때**: ① 읽기 정책과 쓰기 정책을 명령별로 따로 만들고 쓰기 쪽에 `and private.app_write()` ② 로그인 사용자가 부를 security definer 함수는 (읽기만 해도) plpgsql로 쓰고 첫 `begin` 바로 뒤에 `if not private.app_write() then raise exception '앱 서버를 거친 요청만 받습니다' using errcode = '42501'; end if;`, 거절·허용 사례는 `lib/db/app-write-rpc.test.ts`에 ③ grant는 명시하고 `grants.test.ts`의 권한 목록에 더함 ④ `migrations.test.ts`에 역할 × 표지 있음·없음 사례. 표지를 일부러 빼야 하면(앱 밖에서 쓰는 것이 정상인 경우) 예외 목록에 이유를 적습니다 — 그때는 그 쓰기를 서버 액션의 검증에 기대지 못한다는 뜻입니다.
  - **표지가 못 막는 것**: 표지는 「앱 서버를 거쳤다」만 보장합니다.
    - 서버 액션은 여전히 공개 API처럼 불릴 수 있으므로 액션 안의 입력 검증(zod·상한·다시 점검)이 완전해야 합니다. 성과관리팀·관리자가 앱 화면으로 하는 쓰기는 권한 안의 행위라 그대로 허용됩니다(남는 것은 감사 기록).
    - 읽기는 막지 않습니다(범위는 RLS 그대로). 로그인 메일 요청은 표지 밖입니다. 저장소(Storage)는 쓰기 정책만 표지 안(`20261118100000`)이고 읽기 정책·서명 URL은 표지 밖입니다.
    - 비밀이 새면 이 단계 전 상태로 돌아갈 뿐 더 넓게 열리지는 않습니다(서비스 키와 다름) — 키 교체 절차로 닫습니다.
    - 구조 시험은 정책 식의 글자 모양을 봅니다. 맨 위 AND 항으로 들어간 `private.app_write()`가 정말 표지 판정인지(함수 본문)와 행 판정 함수 안쪽은 보지 않으므로, `private.app_write()`를 고치면 `migrations.test.ts`의 거절 사례로 확인합니다.
  - **운영 반영 순서**(어기면 세 표의 쓰기가 모두 거절): ① `20261117120000`(키 표·판정 함수·확인 함수 `public.app_write_probe()` — 정책 변화 없음, 순서 무관) `db:push`와 `APP_WRITE_KEY` 넣은 배포 ② 키 해시 등록(`scripts/db/app-write-key.ts`가 키와 등록 SQL을 만듦 — 비밀 값은 저장소·마이그레이션에 넣지 않음) ③ 배포된 서버에서 `app_write_probe()`가 true인지 확인(운영 관문이 머리글을 DB까지 넘기는지) ④ 그 뒤에만 `20261117130000` `db:push` → 초안 저장·블록 고치기·지표 부분 저장을 화면에서 1회씩. 되돌리기 SQL은 각 마이그레이션 머리 주석.
  - **2·3단계 운영 반영**: 앱 코드 변경이 없으므로 배포 없이 `20261117140000`·`20261117150000`을 `db:push`만 합니다(두 파일은 서로 기대지 않음). 1단계 ③(확인 함수 true)과 B 반영 뒤 화면 저장 확인이 끝난 다음에 합니다 — 표지가 DB까지 오지 않는 상태에서 올리면 앱의 거의 모든 쓰기가 거절됩니다. 되돌리기 SQL은 각 마이그레이션 머리 주석.
  - **첨부 읽은 글(`20261117170000`)**: 3차(`20261117100000`)에서 서비스 키로 옮겼던 읽은 글 7칸 쓰기를 사용자 권한 + 표지로 되돌림(열 단위 update — 카드 자료는 `can_write_card and not card_material_locked`, 보고서 추가자료는 `can_edit_report_content`). 서비스 키는 다시 Auth 관리·감사 기록에만. 반영은 **db:push 먼저 → 배포**(거꾸로면 그 사이 읽은 글 저장 실패). 같은 파일에서 `start_ai_request`가 사용 중지 계정(`private.my_role()` 없음)을 거절.
  - **안전망 — 크기·모양 상한(`20261117160000`)**: 큰 JSON·글 열 22개는 DB CHECK로 바이트 상한(`<표>_<열>_size`), jsonb는 모양(`_shape`), 프로필 이름 100자 — 역할과 무관(서비스 키·스크립트도). 상한(운영 최대의 100배 이상)과 근거는 마이그레이션 머리 주석, 반영 전 확인 SQL도 거기.
  - **키 교체**: 키 표는 교체 기간에만 2행(3행째는 트리거가 거절). 새 해시 등록 → Vercel `APP_WRITE_KEY` 교체·재배포 → 확인 함수 true → 옛 해시 삭제. 유출이 의심되면 바로 합니다.
- **카드 전용 자료 근거 잠금(`20261104100000`, 2026-11-04)**: 확정(제출·승인)한 보고서의 초안·구성안이 근거로 쓴 카드 전용 자료는 누구도 못 지움 — `private.card_material_locked(저장 경로)`(근거 = `card_report_drafts.spec.sources`의 `{kind:"card", id}` 또는 `outline.sources.card`, 잠김 = `report_locked`)를 `card_materials_delete`·`card_materials_objects_delete`에 더하고, 서버 액션 `deleteCardMaterial`은 같은 규칙(`lib/cards/material-lock.ts`)으로 먼저 거절해 목록의 삭제 단추를 끔. 관리자의 과제 영구 삭제(연쇄 삭제)는 RLS 밖이라 그대로 됨. 보고서 추가자료는 원래부터 `can_edit_report_content`로 잠김. 읽은 글 고치기도 같은 잠금(`20261117170000`). 관리자의 과제 영구 삭제는 DB 트리거가 `access_events` `card_purged`(행위자·과제 번호·제목)로 남김(2026-11-17).
- **AI 백그라운드 작업 결과(`20261106100000_ai_results.sql`, 2026-11-06)**: 과제원장 AI 작성지원·질문·리뷰어 코멘트와 경평 초안 AI 요청은 서버 액션이 시작만 하고 `after()`에서 돎(`lib/ai/background.ts` — 상세 `docs/design/ai-assist.md` 「AI 요청 백그라운드 작업」). ① `ai_requests.job`(작업 종류 — `outline`·`alts`·`part`·`plan`·`revise`·`draft`·`assist`·`chat`·`comment`, null이면 동기 호출)은 넣을 때만 정하고 로그인 사용자 update 열 목록에 없음. ② `ai_results`(요청 id = PK·FK `ai_requests` on delete cascade, user_id, card_id → `cards` on delete cascade, feature, result `{ ok, message, data? }`, created_at, expires_at 기본 now()+7일): 읽기는 **본인 행이고 만료 전만**(성과관리팀·관리자도 남의 답은 못 읽음 — `ai_requests`와 다름), 넣기는 본인 이름으로 자기 작업 기록(같은 카드·같은 기능, `job` 있음)에만, 지우기는 본인 행(「기록 지우기」). 만료 행은 읽기 정책이 숨겨 사용자 권한 `delete … where`로는 못 지우므로 문장 트리거 `private.prune_ai_results`(security definer)가 넣을 때마다 모든 만료 행을 지움(정기 작업 라우트는 이 저장소에 없음 — `/api/prep/run`은 서비스 키 처리기라 쓰지 않음). after 안의 쓰기는 시작 때 만든 **사용자 권한 작업 클라이언트**(`lib/supabase/job-client.ts` — 서비스 키 아님): 응답 뒤에는 쿠키를 다시 못 쓰므로 토큰 남은 시간이 25분보다 짧으면 시작(서버 액션)에서 먼저 갱신하고, after 안에서는 그 접근 토큰을 싣고 스스로 갱신하지 않음(리프레시 토큰 교체가 브라우저에 못 가 세션이 끊기는 것을 막음 — `lib/supabase/job-token.ts`). 운영 반영 순서: `db:push` 먼저(새 코드가 열·표에 씀), 그다음 배포.
- **「올린 사람」 이름**은 사용자 권한으로 읽은 프로필만(`lib/users/who.ts` — `profiles_read`라 부서 담당자는 자기 이름만 보이고 같은 팀 동료·성과관리팀은 「다른 사용자」). 서비스 키로 이름을 읽지 않음.
- PGroonga 검색(`*_search*.sql`)은 PGlite에 없어서 호스티드에서 `pnpm db:check-search`로 확인합니다.
- 검색 질의는 반드시 `lib/knowledge/search-query.ts`의 `buildSearchQuery`로 만듭니다. 질의 전체를 정규화하면 `OR`가 낱말 `or`가 됩니다. 긴 실사 답변이 점수를 가져가므로 지적을 찾을 때는 `unit_types`로 거릅니다.
- DB 연결은 Session pooler 주소를 씁니다. 직접 연결(`db.<ref>.supabase.co`)은 IPv6 전용이라 이 네트워크에서 붙지 않습니다.

## 로그인(Supabase 매직링크)

- **계정은 로그인으로 만들지 않습니다**(2026-11-10 보안 점검 T4 H1): 「사용자」 화면(성과관리팀은 기관 메일 부서 담당자만)이나 `pnpm db:user`로만 만들고, Supabase Auth 가입(「Allow new users to sign up」)은 꺼 둡니다 — 켜 두면 공개 키로 Auth API를 직접 불러 외부 메일도 계정을 만들 수 있었음. 로그인은 `shouldCreateUser: false`, 메일 모양만 확인(`isValidEmail`)하고, 등록 안 된 주소에도 보낸 것과 같은 답을 합니다(`isNotRegisteredError` — 계정이 있는지 알리지 않음). 발송 한도(429 — 주소별 재발송 간격은 등록된 주소에만 걸림)도 같은 답이고 서버 로그에만 남깁니다(메일 주소 없이, 2026-11-16 시큐어 코딩 2차 점검). 보낸 화면 문구가 「잠시 뒤 다시 요청」을 안내합니다. 답 만들기는 `lib/users/login.ts requestMagicLink`(시험 `login.test.ts`). 발송 설정 문제(`not authorized` — 기본 SMTP)와 그 밖의 발송 실패는 오류로 알립니다 — 등록된 주소에만 나오므로 그때는 계정 여부가 드러나지만, 운영(사용자 지정 SMTP)에서는 장애 때만 나오고 사용자가 장애를 알아야 해서 둡니다. 응답 시간 차이(등록된 주소만 메일 발송을 기다림)는 응답을 `LOGIN_MIN_MS`(1.5초)까지 채워 줄였습니다(2026-11-17 — 발송이 더 길면 차이가 남음, Supabase를 직접 부르는 길은 CAPTCHA 몫). 로그인·로그인 확인 화면에 오면 이 탭의 카드 AI 대화·검토 메모(sessionStorage `TAB_KEYS`)를 지웁니다(같은 PC 다음 사용자에게 보이던 것). 로그인 화면을 거치지 않은 다른 탭은 기록 값에 둔 주인 사용자 id로 막음(readTabRecord — 2026-11-18). `ALLOWED_EMAIL_DOMAINS`(기본 `kca.kr`)는 성과관리팀이 등록할 수 있는 주소·로그인 화면 예시 주소로만 씁니다. 가입을 꺼도 관리자 API(`auth.admin.createUser`·`generateLink`)는 그대로 됨(운영 절차·근거 `docs/ops/운영-전환.md` §10).
- 공통 지식(조각·문서·원본 파일)은 성과관리팀·관리자 또는 팀이 지정된 활성 사용자만 읽습니다(`private.is_member()`, `20261110100000_member_read_guard.sql`). 팀이 아직 없는 사용자·사용 중지 계정은 못 읽고, 평가단위·팀 이름은 활성 사용자면 읽습니다.
- **사용 중지된 계정**(`profiles.active = false`)은 `requireUser`가 안내가 붙은 `/login?blocked=1`로 보내고(앱 틀·첫 화면도 메뉴를 안 그림), DB는 `my_role()`이 비어 데이터를 막으며, 로그인 링크는 Supabase auth ban으로 막습니다(`setUserActive`).
- **메일 링크가 돌아올 주소는 호출한 주소 기준**(2026-10-12 — `lib/auth/redirect.ts requestOrigin`): 요청 호스트가 이 앱의 주소(`NEXT_PUBLIC_SITE_URL`·Vercel이 넣는 `VERCEL_URL`·`VERCEL_BRANCH_URL`·`VERCEL_PROJECT_PRODUCTION_URL`·localhost)일 때만 그 주소, 아니면 `NEXT_PUBLIC_SITE_URL`(호스트 헤더로 로그인 링크를 남의 주소로 돌리는 것 방지). Supabase Redirect URLs 허용 목록에 그 주소가 있어야 하고(없으면 Site URL 루트로 `/?code=`가 옴 — `proxy.ts`가 `authCallbackSearch`로 `/auth/confirm`에 넘김). 운영 주소·허용 목록은 `docs/ops/운영-전환.md` §2
- 메일 링크는 `/auth/confirm`에서 **버튼을 눌러야** 로그인합니다. 기관 메일 보안 검사기가 링크를 미리 열어도 일회용 토큰이 소모되지 않게 하려는 것입니다. `token_hash`(권장 메일 양식)와 `code`(기본 양식, PKCE) 둘 다 받습니다.
- 세션 갱신과 로그인 전 차단은 `proxy.ts`가 하고(Next 16에서 middleware 대신 proxy — 로그인 없이 열리는 경로는 `lib/auth/public-paths.ts`의 `/login`·`/auth/…`·`/api/prep/run`뿐, 로그인 뒤 돌아갈 주소는 `safeNext`(`lib/nav/return-to.ts isSafeAppPath` — 앱 안 경로만)), 사용자·역할 조회는 `lib/auth/dal.ts`의 `getCurrentUser`·`requireUser`로 데이터 가까이에서 합니다. 권한의 최종 판정은 RLS입니다.
- 서버 액션은 공개 API처럼 다룹니다. 액션 안에서 사용자를 다시 확인합니다.
